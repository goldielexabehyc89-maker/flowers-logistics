# Roadmap

Статусы: `Backlog`, `Ready`, `In progress`, `Review`, `Staging`, `Done`, `Blocked`.

Правила ведения:

- Разработчик обновляет только фактический статус уже утверждённой задачи.
- Новый продуктовый объём не добавляется, этапы не удаляются, приоритеты не меняются
  без решения владельца.
- Завершённый пункт содержит ссылку на commit/PR и реально пройденные проверки.
- `Done` ставится только после фактически выполненных обязательных проверок.

### 1.5. Staging и production на одном сервере — `Done`

Выполнено: PR #5, squash-commit `846b8d8de9e0a91102eadcef780e3a6c425d71d8`.
Фактические проверки в CI: 215 критических тестов, 3 браузерных сценария, `typecheck`,
`lint`, `format`, production-сборка, 4 миграции на чистой PostgreSQL 16 без дрейфа,
миграции и запуск приложения из собранного production-образа, `npm audit` без уязвимостей,
gitleaks без утечек.

Ветка `chore/deploy-single-host`.

Решение владельца: оба окружения живут на одном физическом сервере. Одинаковый `SSH_HOST`
разрешён, но только при различающихся каталоге, Compose-проекте, внешнем порте, томе базы,
файле окружения и маркере; совпадение любого из них — отказ до обращения к серверу.
Подтверждение прохождения staging читается из staging-каталога, маркер production
проверяется отдельно.

Реальные конфигурации выкатки вынесены из Git в игнорируемый каталог `deploy/private/`;
в репозитории остались только шаблоны `deploy/*.conf.example`. Раньше заполнение
отслеживаемого файла делало рабочее дерево грязным, а выкатка запрещает грязное дерево —
команда блокировала сама себя.

Известное ограничение схемы: сбой сервера затрагивает оба окружения сразу. Разнесение
на два сервера не требует изменений в приложении — достаточно указать другой `SSH_HOST`
и отпечаток в конфигурации production.

### Зафиксированные правила этапа 1

- **Конфигурация выкатки живёт вне Git.** В репозитории — только `deploy/*.conf.example`.
  Реальные значения лежат в `deploy/private/`, который целиком в `.gitignore`; секреты
  приложения не попадают и туда — они находятся только на сервере.
- **Внешние outbox-обработчики работают с доставкой «минимум один раз».** Аренда сообщения
  и отметка `OutboxProcessedMessage` защищают от повторного вызова в штатном режиме,
  но не дают гарантии «ровно один раз» при падении процесса между внешним вызовом
  и фиксацией. Поэтому любой будущий запрос наружу — в первую очередь в МойСклад —
  обязан быть идемпотентным по `idempotencyKey`, и ключ должен передаваться во внешний
  запрос с самого начала, а не добавляться потом.

## Этап 2. Read-only исследование МоегоСклада — `Done`

Выполнено: PR #7. Squash-commit фиксируется в начале этапа 3.

**Решения владельца по итогам исследования утверждены** и обязательны для этапа 3:
фильтр заказов — склад «Москва 01 - Маленковская 14, к1 (Ласфлор)» **и** «Способ доставки»
= «Доставка», по стабильным UUID; статус сохраняется и отображается, но заказ не включает
и не исключает, во внутренние состояния не преобразуется и обратно не пишется; источники
полей — `deliveryPlannedMoment`, `shipmentAddress`, «Получатель» целиком, «Комментарий
по доставке», «Время доставки» без резервных источников; неполные данные не отбрасывают
заказ, а поднимают его в «Требует внимания»; наличные — только при «Наличные/карта на ТТ»,
сумма `max(0, sum − payedSum)` целыми минорными единицами; первоначальная загрузка — от
начала текущего дня минус 3 дня без верхней границы, пагинация по 1000; синхронизация —
один `GET` каждые 30 секунд с overlap и дедупликацией по UUID; webhooks не создаются,
чужие подписки не трогаются; интеграция строго read-only.

Готовность к отгрузке с МоимСкладом **не связана** — это будущий внутренний статус
нашего приложения после появления раздела склада.

**Область запросов различается.** Первоначальная загрузка фильтруется на стороне API
по складу, способу «Доставка» и нижней границе даты. Delta-запрос так фильтровать нельзя:
заказ, перенесённый на другой склад или переключённый с «Доставка», выпал бы из выборки
и остался бы незамеченным. Поэтому delta-проход получает все изменённые `customerorder`,
а принадлежность к нашей области определяется локально: вошедший заказ импортируется,
вышедший сохраняется в истории и исключается из активного планирования с записью в аудит
и уведомлением активных `ADMIN` и `LOGISTICIAN`, если он был распределён. Физическое
удаление документа опрос по `updated` вернуть не может — оно обнаруживается только
суточной контрольной сверкой.

Перед реализацией без угадывания определяются два значения: UUID склада (одним read-only
запросом с проверкой единственности) и единицы `sum`/`payedSum` (сверкой с карточкой
заказа). Отложены и не блокируют этап 3: точный маппинг статусов, обратная запись,
судьба «Отгрузки» и отдельный сервисный пользователь.

Полные таблицы — [`docs/MOYSKLAD_MAPPING.md`](docs/MOYSKLAD_MAPPING.md).

<summary>Ход исследования</summary>

Исследование выполнено на реальном аккаунте: 19 `GET`-запросов, ни одной записи, ответов
`429` не было. Результат — [`docs/MOYSKLAD_MAPPING.md`](docs/MOYSKLAD_MAPPING.md).

Установлено: сущность заказа `customerorder`; плановая дата — `deliveryPlannedMoment`;

аккаунт; подписки `customerorder` существуют, но отключены; токен принадлежит пользователю
с полными правами администратора.

Контрольная выборка за 3–5 августа 2026 года подтвердила фильтр: из 579 заказов склада
под условие «Способ доставки» = «Доставка» подошли 336. В них нашлась несостыковка,
из-за которой статус не может подменять фильтр: три заказа с доставкой имели статус
«Самовывоз Завершен».

Read-only невозможно установить судьбу документа «Отгрузка» при отмене, возврате и повторной
доставке — нужен отдельный согласованный эксперимент.

</details>

## Этап 9. Настройка серверов и разрешённый production-запуск — `In progress`

Сервер выбран и базово подготовлен владельцем: Ubuntu 24.04, Docker и Compose, UFW

Staging настроен и **развёрнут** на этом сервере из коммита
`846b8d8de9e0a91102eadcef780e3a6c425d71d8`. Созданы каталог окружения, маркер, каталог
состояния, файл окружения с правами `600` и копия Compose из точного коммита `main`;

контейнеры `healthy`, четыре миграции применены, `/ready` = `200`, OCI-метка образа
совпадает с развёрнутым SHA, приложение слушает только петлевой интерфейс, SHA записан
в `verified-versions`. Доступ до настройки TLS — через SSH-туннель.

Staging **опубликован наружу по HTTPS** через обратный прокси Caddy: сертификат выдан
и продлевается автоматически, HTTP отвечает постоянным редиректом на HTTPS, приложение
по-прежнему слушает только петлевой интерфейс, firewall пропускает снаружи лишь SSH,
80 и 443. Переход ровно один, поэтому в окружении задано `TRUST_PROXY=1`. Проверено
снаружи: главная, вход, `/health`, `/ready` с `database=ok` и `/api/status` отвечают
`200`, защищённый API без токена — `401`.

токен GitHub на сервер не сохранялся.

до `ssh` без внутренних кавычек, из-за чего путь с пробелами разбирался как список
файлов. Исправление закрыто регрессионным тестом.
