# Модуль `delivery` — работа курьера с выданными маршрутами

**Статус: реализован в границах этапа 6.9.**

Курьер видит только `ACTIVE`-маршруты, выданные лично ему, записывает по каждому
заказу результат «Доставлен» или «Не доставлен» и в течение пяти минут может
отменить собственную ошибку. Последний результат маршрута завершает его,
отмена результата — снова открывает.

## Что здесь есть

- `service.ts` — правила и транзакции: справочник причин, список активных доставок,
  запись и отмена результата, история с маскированием персональных данных.
- `routes.ts` — HTTP-слой: `GET /api/delivery/active`, `GET /api/delivery/history`,
  `GET|PUT /api/delivery/failure-reasons`, `POST /api/delivery/orders/:id/result`,
  `POST /api/delivery/attempts/:id/cancel`.
- `delivery.critical.test.ts` — направленные проверки модели, прав, конкурентности,
  пятиминутного окна и московской границы дня.

## Чего здесь нет намеренно

Возврата товара на склад, повторной попытки, передачи заказов другому курьеру,
GPS, фотографий, подписи получателя, SMS и финансовых начислений. Это следующие
пункты этапа 6 и этап 7; выдумывать их поля заранее нельзя.

Клиентской очереди действий нет и не будет: отложенно отправленный результат
приехал бы с чужим временем и поверх чужого решения. Действие выполняется только
online, а потерянный ответ разрешается перечитыванием состояния сервера.

## Ключевые решения

Полное обоснование — `docs/ARCHITECTURE.md` §«Работа курьера и результаты доставки»
и `docs/DOMAIN_STATES.md` §«Результат доставки».

- Результат — неизменяемая попытка `DeliveryAttempt`, а не колонка заказа.
- Единственную активную истину держит уникальный индекс по `activeKey`.
- Повтор запроса возвращает уже записанный результат и не создаёт вторую попытку.
- Название причины хранится снимком: переименование справочника прошлое не правит.
- Маскирует персональные данные сервер; клиент показывает то, что пришло.
