# Модуль `planning` — планирование маршрутов

Ветка 5.4. Оптимизация маршрутов решателем VROOM и автоматические черновики.

## Две фазы

Расчёт и применение разделены намеренно.

1. **Расчёт** создаёт неизменяемое **превью**: маршруты и список неразмещённых
   заказов. Ни одного черновика при этом не появляется.
2. **Применение** — отдельное явное подтверждение человека. Только оно
   превращает план в данные.

План, сразу ставший данными, лишил бы логиста возможности сказать «нет».

## Два снимка, а не один

- `RoutePlanInputSnapshot` создаётся **до** матрицы и решателя. Без него перехват
  брошенной аренды не смог бы продолжить расчёт с первоначальными данными:
  заказы, настройки и склад к тому моменту могли измениться.
- `RoutePlanResultSnapshot` создаётся при переходе в `PREVIEW` и хранит
  нормализованный числовой запрос к решателю и его ответ целиком.

Оба защищены от изменения и удаления триггерами базы. Слоты машин после
постановки запуска тоже неизменяемы.

## Состояния запуска

```
QUEUED ──► COMPUTING ──► PREVIEW ──► APPLIED
   │           │            │
   └───────────┴────────────┴──────► FAILED
                            └──────► EXPIRED
```

Пока запуск не завершён (`QUEUED`, `COMPUTING`, `PREVIEW`), он удерживает
`activeDateKey` — уникальный ключ дня. Два одновременных расчёта одного дня
физически невозможны. Готовое превью не вытесняется молча: новый расчёт того же
дня требует либо явного истечения (`POST /expire`), либо `replacePreviewId`.

## Аренда расчёта

Серверное время, `lockedUntil` и сердцебиение. Перехват допускается только после
истечения срока. Восстановлений после падения процесса не больше трёх
(`RoutePlanRun_shape`), после чего запуск закрывается кодом `RECOVERY_EXHAUSTED`
и день освобождается. Обычная ошибка матрицы или решателя автоматически
**не повторяется**: повтор дал бы тот же результат.

Транзакция не удерживается на время матрицы и решателя.

## Контракт решателя

- обе матрицы (`durations` и `distances`) для каждого использованного профиля;
- целые неотрицательные секунды и метры, дробные округляются **вверх**;
- любая пара `null` останавливает расчёт целиком;
- в запросе только `location_index`, `start_index`, `end_index` — ни адресов,
  ни координат, ни номеров заказов, ни описаний;
- геометрия не запрашивается;
- ответ проверяется как **точное разбиение**: каждый заказ ровно один раз либо
  в маршруте, либо в неразмещённых.

Дополнительно проверяются начало и конец маршрута, известность слота,
вместимость, смена и временные окна.

## Порядок блокировок при применении

```
RoutePlanRun (FOR UPDATE)
→ DeliveryOrder (FOR UPDATE, ORDER BY id)
→ Depot (FOR UPDATE, ORDER BY id)
→ RouteNumberCounter → DeliveryRoute → RouteOrder
→ AuditLog → RealtimeEvent
```

При расхождении входа со снимком превью помечается истёкшим **отдельным
успешным завершением транзакции**, и только затем возвращается `409`.
Исключение внутри транзакции откатило бы и сам переход в `EXPIRED`.

## Что модуль сознательно не делает

- не подтверждает маршруты — это остаётся ручным решением;
- не заменяет существующие черновики;
- не делит день автоматически при превышении предела точек;
- не знает о текущей дорожной обстановке: `trafficMode = STATIC`.
