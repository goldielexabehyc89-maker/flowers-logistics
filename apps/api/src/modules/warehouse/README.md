# Модуль `warehouse` — готовность заказа к отгрузке

Этап 6.1. Границы задаёт активное решение владельца `WH-001`
(`docs/OWNER_DECISIONS.md`).

## Что это

Одно внутреннее состояние заказа: `NOT_READY` (по умолчанию) и `READY`.
Меняет его **только человек** — `ADMIN` или `WAREHOUSE`.

## Чего здесь нет

- товарного учёта: остатков, приёмки поступлений, перемещений и списаний;
- импорта состава заказа (`positions`) из МоегоСклада;
- любой записи в МойСклад: интеграция остаётся read-only, `MS-007` действует;
- вывода готовности из внешнего статуса МоегоСклада — он показывается рядом
  как контекст и состоянием не управляет;
- влияния на `Depot`, снимки планирования, пригодность заказа, жизненный цикл
  и подтверждение маршрута. Неготовность станет обязательным условием только
  будущей отгрузки этапа 6;
- отгрузки маршрутного листа и приёма возврата товара от курьера.

## Почему отдельный модуль

Общий API заказов принадлежит логисту и отдаёт адрес, получателя, комментарий,
деньги и координаты. Складу для решения «готов / не готов» нужен номер заказа,
день и текущее состояние. Добавить роль `WAREHOUSE` в существующий модуль
значило бы открыть ей весь этот состав ради одного признака.

Состав ответа ограничен намеренно: `id`, номер, дата доставки, название внешнего
статуса, готовность, время последнего изменения и версия. Больше ничего.

## Инварианты базы

Держатся не кодом, а PostgreSQL:

- `DeliveryOrder_shipment_readiness_actor` — автор и время последнего изменения
  существуют только вместе. «Известно когда, неизвестно кем» выглядело бы
  доказательством, ничего не доказывая;
- `DeliveryOrder_shipment_readiness_manual` — `READY` невозможно получить без
  следа человека. Иначе один `UPDATE` из консоли сделал бы заказ готовым
  к отгрузке анонимно;
- внешний ключ автора — `ON DELETE RESTRICT`: пользователь не удаляется каскадом;
- индекс `("inScope", "deliveryDate", "shipmentReadiness")` обслуживает рабочий
  список дня.

Физическое удаление заказов и неизменяемость аудита обеспечивают существующие
триггеры; эта ветка их не трогает.

## Конкурентность

Изменение защищено оптимистической блокировкой по версии заказа: два кладовщика
на общем экране — обычная ситуация, а «последний выиграл» означал бы молча
стёртую чужую отметку. Устаревшая версия даёт `409` с `conflict.kind = STALE_VERSION`
и не пишет ничего.

Версия проверяется **до** идемпотентности: совпадение состояния при устаревшей
версии согласием не является.

Повтор того же состояния при актуальной версии идемпотентен — не меняются ни
версия, ни `updatedAt`, ни отметка времени, ни аудит, ни realtime. Иначе двойной
клик выглядел бы в журнале как два решения человека.

## Аудит и realtime

- аудит `ORDER_SHIPMENT_READINESS_CHANGED`: прежнее и новое состояние, версия
  и технические идентификаторы. Номера заказа, адреса, получателя и денег там нет;
- realtime `order.shipment_readiness_changed` для `ADMIN` и `WAREHOUSE`;
  payload — только `orderId`, состояние и версия. Клиент перечитывает список сам.

Обе записи создаются в той же транзакции, что и само изменение.

## Рабочий список

Только `inScope = true`, `sourceArchived = false`, `sourceMissing = false`.
Заказ вне области, архивированный или пропавший из источника скрыт и новую
отметку через API не принимает; сохранённая история при этом не удаляется.

Автоматика готовность не меняет: ни синхронизация, ни повтор снимка, ни выход
из области, ни восстановление источника.
