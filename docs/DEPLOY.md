# Деплой

> **Состояние: сервер выбран и базово подготовлен, staging настроен, приложение
> ещё не развёрнуто.** Наружу ничего не публиковалось: домена, DNS, TLS и обратного
> прокси нет. Production не создавался.
>
> Команды реализованы и без рабочей конфигурации в `deploy/private/` завершаются
> отказом до любого обращения к сети (fail closed). `DRY_RUN=1` показывает план,
> конфигурацию не читает и ничего не выполняет.

## Фактическое состояние

Сервер подготовлен владельцем: Ubuntu 24.04, Docker и Docker Compose, UFW с политикой
«запрещено всё входящее, кроме 22/80/443», автоматические обновления, вход только
по ключу, root-вход и вход по паролю отключены. Адрес, пользователь, отпечаток хоста
и ключи в репозитории не хранятся — они живут в `deploy/private/staging.conf`
и в `~/.ssh` на машине владельца.

На сервере создано только окружение staging: каталог развёртывания, файл `ENVIRONMENT`
со строкой `staging`, каталог `state/`, файл окружения с правами `600` и копия
`docker-compose.deploy.yml` из точного коммита `main`. Секреты окружения сгенерированы
непосредственно на сервере и никуда не выводились.

Не сделано намеренно: production-каталог, `production.env`, том и конфигурация
production не создавались; приложение снаружи недоступно; первый администратор
не создавался.

Для проверки staging до настройки домена используется SSH-туннель на локальный порт
сервера — приложение слушает только петлевой интерфейс, наружу порт не открыт.

## Образы

Образы публикуются в приватный GitHub Container Registry, не в Docker Hub. В pull request
образ только собирается и проверяется; публикация происходит после попадания коммита
в `main` с тегом полного SHA. Тег `latest` не публикуется: выкатка всегда указывает
на конкретный коммит. В образ добавляется метка `org.opencontainers.image.revision`,
и после загрузки скрипт сверяет её с ожидаемым SHA — тег можно перевесить, метку внутри
образа нельзя.

## Модель продвижения

```
локальная разработка
        │  проверки: typecheck, lint, test:critical, build, миграции
        ▼
     staging          ← свой каталог, база, том, файл окружения, порт, бэкапы
        │  фактическая проверка на staging
        ▼
отдельное разрешение владельца
        ▼
    production        ← свой каталог, база, том, файл окружения, порт, бэкапы
```

Универсальной команды `deploy ENV=...` не существует: у каждого окружения своя команда
и своя конфигурация.

## Один сервер, два окружения

Решение владельца: staging и production живут на **одном физическом сервере**. Сначала
запускается staging, позже рядом добавляется production; staging после этого не удаляется
и используется для проверки следующих релизов.

Границей между окружениями служит не хост, а набор ресурсов. Одинаковый `SSH_HOST`
разрешён только тогда, когда различаются **все** критические ресурсы:

| Ресурс                | staging                          | production                          |
| --------------------- | -------------------------------- | ----------------------------------- |
| каталог развёртывания | `/srv/flowers-logistics-staging` | `/srv/flowers-logistics-production` |
| Compose project       | `fl-staging`                     | `fl-production`                     |
| внешний порт          | `127.0.0.1:3001`                 | `127.0.0.1:3000`                    |
| том базы              | `fl-staging-db`                  | `fl-production-db`                  |
| файл окружения        | `staging.env`                    | `production.env`                    |
| маркер окружения      | `staging`                        | `production`                        |

Совпадение любого из них — отказ **до** первого обращения к серверу: общий каталог,
общий Compose project, общий порт, общий том или общий файл окружения означают, что
выкатка одного окружения способна остановить контейнер другого, занять его порт или
переписать его базу. Отдельные deploy lock у окружений сохраняются: локальный — по имени
окружения, удалённый — внутри каталога окружения.

**Честный недостаток этой схемы.** Сбой сервера, исчерпание диска, перегрузка процессора
и перезагрузка затрагивают оба окружения сразу; изоляция здесь логическая, а не физическая.
Резервные копии production тоже лежат на этом же сервере, пока не настроено внешнее
хранилище. Разнесение на два сервера не требует изменений в приложении: достаточно
указать в `deploy/private/production.conf` другой `SSH_HOST` и отпечаток — код выкатки
и Compose остаются прежними.

## Где лежат конфигурации

В Git хранятся **только шаблоны**: `deploy/staging.conf.example` и
`deploy/production.conf.example`. Рабочие конфигурации лежат в `deploy/private/`,
который целиком в `.gitignore`.

```bash
mkdir -p deploy/private
cp deploy/staging.conf.example    deploy/private/staging.conf
cp deploy/production.conf.example deploy/private/production.conf
```

Так сделано потому, что заполнение отслеживаемого файла делало бы рабочее дерево грязным,
а выкатка запрещает грязное дерево — команда блокировала бы сама себя. Путь к конфигурации
вычисляется от расположения скрипта и не зависит от того, где именно лежит репозиторий.

Секреты приложения (пароль базы, `AUTH_*`, токены) в эти файлы **не попадают**: они лежат
только в файле окружения на самом сервере. `DRY_RUN=1` конфигурацию не открывает вовсе —
печатает план и завершается, поэтому сухой прогон работает и на свежем клоне.

Compose-файл один — `deploy/docker-compose.deploy.yml`. Имя проекта, внешний порт, файл
окружения, имя тома и маркер окружения он берёт из конфигурации выкатки, поэтому значение
задаётся ровно в одном месте и не может разъехаться между копиями файла. Приложение
слушает только петлевой интерфейс; обратный прокси, DNS и TLS настраиваются отдельно
при настройке сервера.

## Интерфейс команд

```bash
make deploy-staging    VERSION=<полный-40-символьный-sha>
make deploy-staging    VERSION=<полный-40-символьный-sha> DRY_RUN=1
make deploy-production VERSION=<полный-40-символьный-sha>
make deploy-production VERSION=<полный-40-символьный-sha> DRY_RUN=1

# эквивалентный прямой вызов скрипта
./deploy/scripts/deploy-staging.sh --version <sha> --dry-run
```

`--dry-run` как аргумент `make` не используется: его перехватывает сам Make.
Переключатель передаётся переменной `DRY_RUN=1`; флаг `--dry-run` понимает только скрипт.

## Обязательные проверки внутри скриптов

Общие:

- `set -euo pipefail`, корень репозитория вычисляется от расположения самого скрипта,
  все пути в кавычках (путь содержит пробелы и кириллицу);
- обязательный **полный** commit SHA, фактически присутствующий в `origin/main`;
- запрет при грязном рабочем дереве;
- deploy lock, не допускающий двух одновременных запусков;
- секреты не передаются аргументами командной строки и не попадают в логи;
- отчёт о фактически развёрнутом SHA;
- `DRY_RUN=1` печатает план и не производит внешних изменений;
- отказ до обращения к серверу, если критические ресурсы окружений совпадают;
- отсутствие рабочей конфигурации в `deploy/private/` — тоже отказ до SSH.

Staging:

- сверка маркера окружения **в staging-каталоге** со значением `staging`
  и проверка host fingerprint;
- проверка изоляции от production, как только его конфигурация создана;
- запись факта успешной проверки версии в `state/verified-versions`
  **внутри staging-каталога** — она нужна production-команде.

Production:

- сверка маркера окружения **в production-каталоге** со значением `production`
  и проверка host fingerprint;
- допускается только SHA, ранее успешно проверенный на staging. Подтверждение
  читается **из staging-каталога отдельным соединением** по staging-конфигурации,
  с собственным `known_hosts` и сверкой маркера `staging`, и только затем команда
  обращается к production-каталогу. Production-каталог доказательством прохождения
  staging служить не может — иначе production подтверждал бы выкатку сам себе;
- обязательный бэкап базы и проверка свободного места до начала выкатки;
- вывод домена, хоста, каталога, порта и ручной ввод слова `PRODUCTION`;
- выполняется только по отдельной прямой команде владельца.

## Миграции при выкатке

Только `prisma migrate deploy` — forward-only, без интерактивных подтверждений.
`prisma migrate reset` и любые деструктивные операции на staging и production запрещены.
Порядок: бэкап → применение миграций → запуск нового образа → проверка `/ready`.

CLI Prisma входит в обычные зависимости и лежит внутри production-образа, поэтому
миграции применяются тем, что уже развёрнуто, и выкатка не зависит от доступности
реестра npm. CI проверяет это на собранном образе: запускает из него
`npx --no-install prisma migrate deploy` на чистой PostgreSQL 16, затем поднимает
приложение из того же образа и дожидается `/ready`. Публикуется в GHCR ровно тот
образ, который прошёл проверку.

## Что настраивается вместе с владельцем

Сам сервер, DNS, TLS, обратный прокси, хранилище резервных копий и файлы окружения —
отдельная задача. Пока для окружения нет конфигурации в `deploy/private/`, его команда
выкатки завершается отказом до любого обращения к сети.

Что должно быть в каталоге окружения на сервере:

- `ENVIRONMENT` — файл с единственной строкой `staging` или `production`;
- `docker-compose.deploy.yml` — копия файла из репозитория;
- `staging.env` / `production.env` — секреты окружения, только на сервере, права `600`;
- `backup.sh` — команда резервного копирования (обязательна для production);
- `state/` — каталог, в котором staging ведёт `verified-versions`.

Секреты окружения генерируются **на самом сервере** криптографически стойким генератором
и не проходят через машину разработчика: `AUTH_ACCESS_TOKEN_SECRET` и `AUTH_PIN_PEPPER`
не короче 32 байт, `AUTH_REFRESH_REPLAY_KEY` — ровно 32 байта в base64, пароль базы
отдельный для каждого окружения.

## Доступ к приватному образу с сервера

Пакет в GHCR приватный, поэтому серверу нужен credential для `docker login ghcr.io`.
Использовать для этого широкий токен GitHub нельзя: он даёт доступ к репозиториям
и рабочим процессам, а серверу требуется только чтение одного пакета. Нужен отдельный
credential с единственным правом `read:packages`, передаваемый в `docker login`
через stdin и не попадающий ни в историю команд, ни в логи, ни в репозиторий.

Пока такого credential нет, выкатка останавливается до `docker login`: подготовка
сервера при этом выполняется полностью.
