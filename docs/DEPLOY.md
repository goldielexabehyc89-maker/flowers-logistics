# Деплой

> **Состояние: серверы не выбраны, наружу ничего не разворачивалось.**
> Команды реализованы и до заполнения конфигураций завершаются отказом до любого
> обращения к сети (fail closed). `DRY_RUN=1` показывает план и ничего не выполняет.

## Образы

Образы публикуются в приватный GitHub Container Registry, не в Docker Hub. В pull request
образ только собирается и проверяется; публикация происходит после попадания коммита
в `main` с тегом полного SHA. Тег `latest` не публикуется: выкатка всегда указывает
на конкретный коммит. В образ добавляется метка `org.opencontainers.image.revision`,
и после загрузки скрипт сверяет её с ожидаемым SHA — тег можно перевесить, метку внутри
образа нельзя.

## Модель продвижения

```
локальная разработка
        │  проверки: typecheck, lint, test:critical, build, миграции
        ▼
     staging          ← отдельный сервер, база, volumes, домен, секреты, бэкапы
        │  фактическая проверка на staging
        ▼
отдельное разрешение владельца
        ▼
    production        ← отдельный сервер, база, volumes, домен, секреты, бэкапы
```

Общих ресурсов между staging и production нет. Универсальной команды `deploy ENV=...`
не существует: у каждого окружения своя команда, свой конфигурационный файл и свой SSH-target.

## Интерфейс команд

```bash
make deploy-staging    VERSION=<полный-40-символьный-sha>
make deploy-staging    VERSION=<полный-40-символьный-sha> DRY_RUN=1
make deploy-production VERSION=<полный-40-символьный-sha>
make deploy-production VERSION=<полный-40-символьный-sha> DRY_RUN=1

# эквивалентный прямой вызов скрипта
./deploy/scripts/deploy-staging.sh --version <sha> --dry-run
```

`--dry-run` как аргумент `make` не используется: его перехватывает сам Make.
Переключатель передаётся переменной `DRY_RUN=1`; флаг `--dry-run` понимает только скрипт.

## Обязательные проверки внутри скриптов

Общие:

- `set -euo pipefail`, корень репозитория вычисляется от расположения самого скрипта,
  все пути в кавычках (путь содержит пробелы и кириллицу);
- обязательный **полный** commit SHA, фактически присутствующий в `origin/main`;
- запрет при грязном рабочем дереве;
- deploy lock, не допускающий двух одновременных запусков;
- секреты не передаются аргументами командной строки и не попадают в логи;
- отчёт о фактически развёрнутом SHA;
- `DRY_RUN=1` печатает план и не производит внешних изменений.

Staging:

- сверка environment marker цели со значением `staging` и проверка host fingerprint;
- отказ, если целью оказался production-хост;
- запись факта успешной проверки версии на staging — она нужна production-команде.

Production:

- сверка environment marker цели со значением `production` и проверка host fingerprint;
- отказ, если целью оказался staging-хост;
- допускается только SHA, ранее успешно проверенный на staging;
- обязательный бэкап базы и проверка свободного места до начала выкатки;
- вывод домена и хоста и ручной ввод слова `PRODUCTION` для подтверждения;
- выполняется только по отдельной прямой команде владельца.

## Миграции при выкатке

Только `prisma migrate deploy` — forward-only, без интерактивных подтверждений.
`prisma migrate reset` и любые деструктивные операции на staging и production запрещены.
Порядок: бэкап → применение миграций → запуск нового образа → проверка `/ready`.

## Что настраивается вместе с агентом-администратором

Реальные серверы, DNS, TLS, firewall, хранилище резервных копий и секреты окружений.
Провайдер не выбирается разработчиком самостоятельно. До этого момента:

- значения `APP_ENVIRONMENT_MARKER`, SSH-targets и host fingerprints в `deploy/*.conf`
  остаются незаполненными;
- обе команды деплоя завершаются отказом с понятным сообщением;
- никакой выкатки наружу не производится.
