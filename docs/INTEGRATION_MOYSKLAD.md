# Интеграция с МоимСкладом

> **Состояние: не подключена, но исследована.** Кода интеграции нет, запись
> `IntegrationStatus` для провайдера `moysklad` по-прежнему `NOT_CONFIGURED`.
> Read-only исследование реального аккаунта выполнено: фактические сущности, поля,
> статусы, атрибуты, webhooks и лимиты зафиксированы в
> [`docs/MOYSKLAD_MAPPING.md`](MOYSKLAD_MAPPING.md).
>
> Исследование выполнялось только `GET`-запросами. Ни одной записи в аккаунт
> не производилось: заказы, отгрузки, статусы, атрибуты и webhooks не создавались
> и не изменялись.

## Принципиальные договорённости

- МойСклад — **единственный** внешний источник заказов. Bitrix24 не используется.
- При первом подключении импортируются доставки с текущего дня на 30 дней вперёд; окно
  ежедневно сдвигается, а уже загруженные незавершённые заказы отслеживаются независимо от даты.
- Более старые заказы до запуска не импортируются. Исключаются только заказы с явно
  указанным самовывозом; всё остальное в окне импортируется, а неоднозначные значения
  получают признак «требует внимания».
- **Деньги и время.** Денежные значения API переводятся в целые копейки и хранятся только
  целыми; числа с плавающей точкой для денег не используются. Даты МоегоСклада
  интерпретируются в `Europe/Moscow` с сохранением исходного значения. Подробности —
  в `docs/MOYSKLAD_MAPPING.md`.
- Ключ идемпотентности — внутренний UUID МоегоСклада. Номер заказа только отображается
  и участвует в поиске. Повторные webhooks дубликатов не создают.
- Дата доставки в нашем приложении **только для чтения**; меняется исключительно в МоемСкладе.
- Адрес, интервал, имя получателя, телефон и комментарий логист может исправить с отправкой
  обратно в МойСклад.
- При событии загружается полная актуальная карточка заказа; сравниваются и журналируются
  все импортируемые поля, а не только логистические.

## Что установлено исследованием

Полные таблицы — в [`docs/MOYSKLAD_MAPPING.md`](MOYSKLAD_MAPPING.md). Кратко:

1. Сущность заказа доставки — `customerorder`; набор импортируемых полей зафиксирован.
2. Статусов 32, из них к нашей доставке относится ограниченная часть; сопоставление
   с `docs/DOMAIN_STATES.md` предложено, но требует утверждения владельцем.
3. Плановая дата доставки — стандартное поле `deliveryPlannedMoment`.
4. **Интервал доставки отдельными полями не существует** — есть только свободный текст
   в атрибуте «Время доставки». Это открытый вопрос: либо два новых атрибута времени,
   либо разбор текста с неизбежными «нераспознанными интервалами».
5. Явного признака готовности к отгрузке нет — готовность выражается статусом; какой
   именно статус её означает, решает владелец.
6. Признак доставки и самовывоза **есть** — атрибут «Способ доставки» со справочником
   из шести значений. Добавлять атрибут «Способ получения» не требуется, правило
   «отсутствие адреса не признак самовывоза» соблюдается. Импорт исключает **только**
   заказы с явным значением «Самовывоз»; «Розница», «ОПТ», `-` и незаполненный атрибут
   импортируются с признаком «требует внимания». Статус для исключения заказа
   не используется.
7. Способ оплаты — атрибут «Тип Оплаты» со справочником из 19 значений. Отдельного
   булева признака онлайн-оплаты нет; наличная сумма выводится из `sum` и `payedSum`.
8. Доступны на запись: адрес, комментарий, статус и пользовательские атрибуты.
   Суммы вычисляемые и записи не подлежат.
9. Заказ связан с «Отгрузкой» полем `customerOrder` документа `demand` и обратным
   массивом `demands`.
10. Токен принадлежит пользователю с полными правами администратора — это не сервисный
    пользователь. Отдельного пользователя с минимальными правами заводит владелец.

## Что read-only установить нельзя

Судьба документа «Отгрузка» при отмене, возврате и повторной попытке, поведение остатков,
резервов и оплат. Для этого нужен эксперимент с записью в аккаунт, который в исследование
не входил и без отдельного разрешения владельца не выполняется.

## Что нельзя делать до утверждения маппингов

**Не кодировать названия полей, статусов и атрибутов, не подтверждённые исследованием,
и не выбирать спорные трактовки самостоятельно.** Открытые вопросы перечислены таблицей
в `docs/MOYSKLAD_MAPPING.md` и закрываются решением владельца. Допустимы интерфейсы
адаптера и disabled/mock-реализация.

## Планируемая механика обмена

- **Основной механизм** — идемпотентные webhooks.
- **Резерв** — delta polling примерно раз в 3–5 минут и полная ночная сверка.
  Курсором служит `updated`, но **не как строгая граница «больше последнего виденного»**:
  у нескольких заказов метки совпадают, а изменение, зафиксированное с опозданием,
  получает более раннюю метку и провалилось бы мимо курсора. Поэтому каждый проход читает
  окно с перекрытием (`updated >= курсор − overlap`), результат дедуплицируется по UUID,
  обработка идемпотентна, а курсор двигается только на подтверждённо обработанные записи.
- **Лимиты — наблюдённые.** API возвращает `X-RateLimit-Limit: 45` при
  `X-Lognex-Retry-TimeInterval: 3000`, то есть **45 запросов, равномерно выполняемых
  за интервал 3000 мс**, и лимит относится **ко всему аккаунту**, а не к приложению.
  Механизм «скользящим окном» не называем: наблюдением это не подтверждается.
  При `429` пауза берётся из `X-Lognex-Retry-After`, а не из `X-Lognex-Retry-TimeInterval`
  (последний описывает интервал лимита). Токен используется не только нашим приложением:
  при темпе один запрос в 1,5 секунды `X-RateLimit-Remaining` уже показывал 43 из 45.
  Поэтому нужен отдельный сервисный пользователь с минимальными правами, а наш стартовый
  режим — **консервативный: 1 одновременный запрос и не более 1 запроса в секунду**
  с замедлением по `X-RateLimit-Remaining`. Повышение темпа — только по наблюдениям
  на реальной нагрузке.
  Обязательны batch-запросы, дедупликация и приоритетная очередь: перед отгрузкой выполняется
  одно пакетное обновление заказов маршрута, а не запрос на каждый заказ.
- **Таймауты и повторы.** Каждый запрос ограничен по времени; повторы конечны, с экспоненциальной
  паузой. На `429` — пауза с backoff и ограниченное число попыток, затем честная ошибка.
  Бесконечных повторов не существует.
- **Доставка событий наружу** — только через серверный транзакционный outbox, независимо
  от клиента.

## Конфликты и недоступность

- При недоступности API разрешены экстренные локальные исправления адреса, интервала,
  получателя, телефона и комментария с обязательной причиной и отметкой «Ожидает отправки».
  Они сразу используются в работе и отправляются через outbox после восстановления.
- Если после восстановления одинаковое поле отличается локально и в МоемСкладе, значения
  **не перезаписываются молча**: оба показываются `ADMIN`/`LOGISTICIAN` с требованием выбора.
- Известный конфликт блокирует подтверждение и отгрузку и **не обходится** аварийной кнопкой.
- Временная недоступность API — отдельное состояние с аварийной работой по кэшу; один сетевой
  сбой не считается длительной аварией, сначала выполняется retry.
- В интерфейсе отображается статус интеграции и число ожидающих операций; технические детали
  ошибок доступны администратору. Очищенные от секретов и PII детали хранятся
  в `IntegrationStatus.details`.

## Секреты

Токен МоегоСклада хранится в переменных окружения сервера (`MOYSKLAD_API_TOKEN`).
В `SystemSetting` он не попадает никогда — эта таблица предназначена только для несекретных
настроек. API не возвращает токен после сохранения: только признак «настроено» и маска.
В клиентскую сборку, Git, логи и отчёты токен не попадает.
