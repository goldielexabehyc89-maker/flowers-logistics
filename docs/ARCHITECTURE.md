# Архитектура

## Общая форма

Модульный монолит на TypeScript. Один репозиторий и одно разворачиваемое приложение:
в production один Node-процесс обслуживает API и отдаёт собранный web-клиент.
Микросервисов, Kubernetes и Redis нет намеренно — нагрузка (200 заказов в обычный день,
более 2000 в праздничный, 50+ курьеров) не требует распределённой системы, а лишние
компоненты увеличивают стоимость и число режимов отказа.

```
браузер / PWA
     │  HTTP + SSE
     ▼
┌─────────────────────────────────────────┐
│ Node 24.19.0 (один процесс)             │
│  Fastify: API + статика web-клиента     │
│  platform/  конфиг, логи, БД, HTTP      │
│  modules/   auth, users, couriers, …    │
│  worker:    outbox (в том же процессе)  │
└──────────────┬──────────────────────────┘
               │ Prisma 7 + @prisma/adapter-pg
               ▼
        PostgreSQL 16
   данные · outbox · realtime-события · аудит
```

## Границы модулей

`apps/api/src/modules/` — каждый модуль владеет своей предметной областью и не лезет
в таблицы соседа напрямую.

| Модуль                               | Этап               | Состояние         |
| ------------------------------------ | ------------------ | ----------------- |
| `health`                             | 1                  | реализован        |
| `auth`, `users`, `couriers`, `audit` | 1 (ветка auth)     | реализованы       |
| `settings`                           | 5.4                | реализован        |
| `depots`, `planning`                 | 5.4                | реализованы       |
| `realtime`, `outbox`                 | 1 (ветка realtime) | каталоги-заглушки |
| `orders`, `integrations`             | 2–3                | каталоги-заглушки |
| `routing`                            | 4–5                | каталог-заглушка  |
| `delivery`, `notifications`          | 6                  | каталоги-заглушки |
| `finance`, `reports`                 | 7                  | каталоги-заглушки |

`platform/` — общая инфраструктура: конфигурация, логирование, доступ к БД, HTTP-слой, ошибки.
`packages/shared` — типы, коды ошибок и русские сообщения, общие для сервера и клиента.

## Технические решения

Подробности и обоснования — в `docs/adr/`.

- **Node.js 24.19.0** зафиксирован одинаково в `.nvmrc`, `engines`, Docker и CI.
- **Prisma 7.9.1** с driver adapter `@prisma/adapter-pg`: строка подключения задаётся
  в `prisma.config.ts`, а не в `schema.prisma` (требование Prisma 7).
- **TypeScript 5.9.3**, не 7.x: `typescript-eslint@8` объявляет peer-диапазон
  `typescript >=4.8.4 <6.1.0`. Обновление — после поддержки в цепочке линтера.
- **Fastify 5** для API, **React 19 + Vite 8** для клиента, **Vitest 4** для тестов.
- **Без Redis**: rate limit, блокировки и очередь живут в PostgreSQL.

## Данные и инварианты

Схема этапа 1 описана в `prisma/schema.prisma`. Ключевые инварианты защищены базой,
а не только кодом:

- **Аудит неизменяем** — триггеры блокируют `UPDATE` и `DELETE` на `AuditLog`.
- **Пользователи не удаляются** — триггер блокирует `DELETE` на `User` и `CourierProfile`,
  внешние ключи используют `ON DELETE RESTRICT`. Недоступность выражается статусом `FROZEN`.
- **Один активный код активации на пользователя** — частичная уникальность выражена через
  nullable-колонку `activeKey` с уникальным индексом (NULL в PostgreSQL не конфликтуют).
  Тот же приём используется для «ровно одна текущая версия настройки» (`currentKey`).
  Дополнительно `CHECK`-ограничения требуют `activeKey = userId` и `currentKey = key`:
  без них уникальность держалась бы только на дисциплине приложения, и произвольное
  значение в колонке обошло бы правило.
- **Идемпотентность outbox** — уникальный `idempotencyKey` на сообщение и уникальная пара
  `(handlerName, idempotencyKey)` на факт обработки.

Проверки этих инвариантов выполняются на реальной PostgreSQL 16
(`apps/api/src/platform/db-invariants.critical.test.ts`).

## Авторизация

- Access-токен: JWT HS256, TTL 10 минут, хранится в памяти клиента, передаётся
  в заголовке `Authorization`.
- Refresh-токен: непрозрачное случайное значение в httpOnly/Secure/SameSite=Strict cookie
  на `/api/auth`; в базе только хеш. Каждое устройство — отдельная семья (`familyId`).
- Ротация сериализуется через `SELECT … FOR UPDATE` по корню семьи, поэтому две активные
  ветки токенов возникнуть не могут.

| Состояние предъявленного токена                                          | Ответ                                                                                             | Семья               |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- | ------------------- |
| текущий, не ротирован                                                    | ротация: выдаётся преемник; в старой строке на 30 с сохраняется `successorTokenEnc` (AES-256-GCM) | одна активная ветка |
| ротирован, `now ≤ graceUntil`, преемник ещё не ротирован                 | тот же преемник + новый access-токен, повторной ротации нет                                       | одна активная ветка |
| **ротирован, преемник уже ротирован**                                    | **reuse: 401, отзыв всей семьи, аудит**                                                           | семья мертва        |
| ротирован, `now > graceUntil`                                            | reuse: 401, отзыв всей семьи, аудит                                                               | семья мертва        |
| неизвестен / отозван / пользователь FROZEN / устаревший `sessionVersion` | 401 без побочных эффектов кроме аудита                                                            | без изменений       |

Мгновенный отзыв доступа: каждый запрос сверяет `status = ACTIVE` и `sessionVersion` токена
с базой. Заморозка и сброс PIN инкрементируют `sessionVersion` и помечают все сессии
отозванными — доступ пропадает сразу, не дожидаясь истечения access-токена.

**Известное ограничение.** Очистка `successorTokenEnc` ленивая: копия затирается при
следующей работе с той же семьёй сессий. Если устройство замолчало сразу после ротации,
зашифрованная копия остаётся в базе дольше тридцати секунд. Глобальная фоновая очистка
обязательна до staging и production и зафиксирована в `ROADMAP.md`, пункт 1.4.

## Защита от перебора

Счётчик неудач **не обнуляется** по истечении блокировки: иначе, переждав тридцать секунд,
можно было бы вечно оставаться на первом пороге, и уровни 5, 7 и 10 стали бы недостижимы.
Счётчик сбрасывает только успешный вход или активация. Инкремент по каждому ключу
сериализуется advisory-блокировкой: параллельные попытки иначе прочитали бы одно значение
и часть счёта потерялась бы. При отказе `429` клиент получает заголовок `Retry-After`;
технические детали в тело ответа не попадают.

## Код активации

Код активации применим **только** к пользователю в статусе `PENDING_ACTIVATION` — и при
активации, и при перевыпуске. Для действующего сотрудника существует отдельная операция
сброса PIN, которая аудируется и отзывает все сессии. Без этого ограничения код активации
позволял бы заменить чужой PIN в обход администратора.

Погашение кода и перевод пользователя в `ACTIVE` выполняются условно внутри одной
транзакции, поэтому из двух одновременных запросов с одним кодом выигрывает ровно один:
второй откатывается целиком, не создавая ни сессии, ни успешной записи аудита.

## Клиентское приложение

React 19 + Vite, маршрутизация `react-router`, серверные данные и мутации —
`@tanstack/react-query`. Состояние авторизации живёт в React Context; отдельного
state-management нет намеренно: данные приходят с сервера и кэшируются запросами.

**Хранение токена.** Access-токен существует только в памяти экземпляра `ApiClient`
(приватное поле). Ни `localStorage`, ни `sessionStorage`, ни IndexedDB, ни URL,
ни кэш service worker не используются: токен, попавший в хранилище, переживает вкладку
и доступен любому скрипту на странице. Refresh-токен браузеру не виден вовсе — он лежит
в httpOnly cookie на пути `/api/auth`.

**Восстановление сессии.** При запуске приложение выполняет `POST /api/auth/refresh`.
Успех восстанавливает пользователя без повторного входа, отказ ведёт на экран входа.

**Single-flight refresh.** При ответе `401` выполняется один общий refresh на все
параллельные запросы и ровно одна повторная попытка. Без этого десять одновременных `401`
запустили бы десять ротаций, и все, кроме одной, сервер счёл бы повторным использованием
токена — семья сессий была бы отозвана. Повтор выполняется без права на ещё один refresh,
поэтому цикл невозможен.

Клиент считает поколения токена. Если запрос ушёл со старым токеном, а к моменту его `401`
токен уже обновил другой запрос, второй refresh не запускается — достаточно повторить запрос
с новым токеном.

Сессия считается потерянной, если refresh не удался **или** единственная повторная попытка
снова вернула `401`. В обоих случаях память очищается, кэш запросов сбрасывается,
а интерфейс возвращает на вход — уведомление отправляется ровно один раз, сколько бы
запросов ни завершилось `401` одновременно.

**Права.** Интерфейс скрывает недоступные разделы, но это удобство, а не защита:
решение всегда принимает сервер. Пока сессия проверяется, показывается экран ожидания —
административные пункты не должны кратко мелькать у пользователя, которому не положены.

**Граница кэша PWA.** Service worker кэширует только оболочку и статические ресурсы.
Не кэшируются: `/api`, `/health`, `/ready`, любые запросы с заголовком `Authorization`,
любые ответы с `Cache-Control: no-store` и все запросы, кроме `GET`. Офлайн-очереди
действий нет: без сети рабочие операции честно сообщают «Нет связи». Правила описаны
в `apps/web/src/pwa/cache-policy.ts` и покрыты критическими тестами; `public/sw.js`
повторяет их без сборщика, потому что подключается отдельным скриптом.

## Права при конкурентных изменениях

Операции заморозки, разморозки, перевыпуска кода и сброса PIN блокируют строку целевого
пользователя (`SELECT … FOR UPDATE`) и перечитывают его роли и статус **внутри** транзакции.
Проверка прав до транзакции создавала гонку: пока логист открывал карточку курьера,
администратор мог выдать этому курьеру привилегированную роль.

## Realtime

- Событие пишется в таблицу `RealtimeEvent` **в одной транзакции** с бизнес-изменением:
  ситуация «изменение есть, а события нет» невозможна.
- `LISTEN/NOTIFY` — только ускоритель доставки, не источник истины и не канал передачи данных.
- При переподключении клиент присылает `Last-Event-ID`, сервер читает пропущенное **из базы**,
  поэтому перезапуск приложения и переключение на другой экземпляр восстановление не ломают.
- Срок хранения событий — 24 часа. За его пределами клиент получает `resync-required`
  и выполняет полный рефетч.
- **Фильтрация обязательна**: событие доставляется, только если адресовано лично пользователю
  или одной из его ролей. Правило вынесено в чистую функцию `isEventVisibleTo`
  (`packages/shared/src/realtime.ts`) и покрыто критическими тестами: курьер не получает
  ни административных, ни чужих персональных событий. Событие без адресата не видит никто.

Канал реализован как SSE на `GET /api/realtime/events`. Токен передаётся только заголовком
`Authorization`: нативный `EventSource` не умеет этого, поэтому клиент читает поток через
`fetch`. Токен в URL попал бы в логи прокси, историю браузера и `Referer`.

Сервер держит heartbeat раз в 15 секунд. Перед выдачей каждой пачки событий он в **той же
транзакции** (`repeatable read`) перечитывает статус пользователя, `sessionVersion`, живость
семьи устройства и **актуальные роли** — и только потом читает события. Общий снимок
обязателен: при раздельных запросах между проверкой и чтением успевала бы пройти смена
ролей, и клиент получил бы пачку по уже отобранным правам. Роли берутся из базы, а не из
токена: токен был выдан раньше и мог описывать доступ, которого больше нет. Недействительная
сессия закрывает канал событием `session-closed` до отправки любых новых событий, поэтому
заморозка, сброс PIN и выход со всех устройств действуют сразу, а не ждут переподключения.
Ошибки базы в фоновом проходе перехватываются: сбой не рвёт поток и не роняет процесс
необработанным rejection.

Задержка видимости: `bigserial` не гарантирует, что порядок фиксации транзакций совпадает
с порядком идентификаторов. Поэтому выдаются только события, ставшие старше окна видимости
(300 мс) — иначе курсор перепрыгнул бы через транзакцию с меньшим `id`, зафиксированную позже.
Ограничение подхода: транзакция длительностью в минуты всё равно может опоздать; при нашей
длительности транзакций окна достаточно.

Клиент переподключается с экспоненциальной задержкой и разбросом, держит ровно один канал,
останавливается при выходе и использует общий single-flight refresh при `401`. События
`session-closed` и `session.revoked`, как и окончательный `401`, ведут в единый механизм
потери сессии из `AuthContext`: очищаются токен, пользователь и кэш запросов, после чего
маршрутизация сама показывает экран входа — без перезагрузки страницы.

## Транзакционный outbox

Запись в `OutboxMessage` создаётся в той же транзакции, что и бизнес-изменение. Воркер
работает в том же процессе приложения: захват выполняется одним запросом
`FOR UPDATE SKIP LOCKED` с немедленным переводом в `PROCESSING`, поэтому два экземпляра
приложения не возьмут одно сообщение. Зависшие `PROCESSING` возвращаются в очередь
по истечении аренды: процесс мог быть убит между захватом и завершением.

Аренда живёт, пока жив захвативший её процесс. Во время прохода фоновый таймер продлевает
`lockedAt` у всех ещё не обработанных сообщений пачки — и у того, что обрабатывается прямо
сейчас, и у последних в пачке, до которых очередь дойдёт нескоро. Поэтому обработчик может
длиться дольше срока аренды, не рискуя быть выполненным вторым воркером; если процесс умер,
таймер умер вместе с ним и аренда истекает честно. Дополнительно все переходы в `DONE`,
`ERROR` и `DEAD` выполняются условно — только при `status = PROCESSING` и совпадении
`lockedBy`. Воркер, у которого аренду всё же перехватили, не имеет права переписать результат
нового владельца. Ручной повтор из интерфейса берёт строку под `FOR UPDATE` и меняет только
сообщение в состоянии `ERROR` или `DEAD`, поэтому не может забрать сообщение у работающего
обработчика.

Постановка сообщения выполняется одним запросом со `skipDuplicates` (`ON CONFLICT DO
NOTHING`): проверка «сначала найти, потом создать» при гонке приводила бы к нарушению
уникального индекса, потому что параллельные транзакции не видят незафиксированных вставок
друг друга.

Остановка процесса корректная: очередь и фоновые очистки запрещают новые проходы и
дожидаются начатого, и только после этого закрывается соединение с базой.

Обработчик выбирается только из явного списка тем — запись в базе не может заставить
приложение выполнить произвольное действие. Повторы идут с экспоненциальным backoff,
после исчерпания попыток сообщение переходит в `DEAD`. Текст ошибки очищается от секретов
и обрезается по длине. Идемпотентность обеспечивается парой `(handlerName, idempotencyKey)`.

Администратор видит список ошибок и может повторить отправку; исходный payload наружу
не отдаётся, ручной повтор пишется в аудит. Клиентского outbox для курьерских статусов нет
и не будет: статус записывается только при наличии сети.

## Фоновые очистки

Две задачи выполняются при старте и затем по расписанию: затирание просроченных копий
`successorTokenEnc` и удаление `RealtimeEvent` за пределами срока хранения. Задачи не
запускаются параллельно сами с собой, интервалы и часы инъецируются в тестах, содержимое
копии преемника никогда не логируется — только количество затронутых строк.

## Секреты

- `SystemSetting` хранит **только несекретные** значения (адрес склада, вместимость,
  максимальная длительность маршрута, сервисное время, резерв, флаг «Логист может отгружать»).
  На запись действует whitelist ключей и запрет имён, похожих на секрет
  (`token|secret|key|password|apikey|credential`).
- Секреты (токен МоегоСклада, ключи карт) хранятся в переменных окружения. Когда потребуется
  хранение на стороне сервера, будет добавлено отдельное зашифрованное хранилище
  (AES-256-GCM, ключ из окружения) — спекулятивных таблиц сейчас не создаётся.
- API никогда не возвращает секрет после сохранения: только `configured: true|false`
  и маскированный «хвост». В клиентскую сборку секреты не попадают.
- `IntegrationStatus.details` проходит очистку: без токенов, cookies, заголовков и PII.

## Сеть и доверие к прокси

`trustProxy` по умолчанию **выключен**. Безусловное доверие заголовку `X-Forwarded-For`
позволило бы клиенту подделать свой IP-адрес и обойти rate limit и прогрессивную блокировку
перебора, если приложение окажется доступно не только через доверенный reverse proxy.

Доверенные источники задаёт переменная `TRUST_PROXY`: список IP/CIDR либо число доверенных
переходов. Значение `true` запрещено — приложение откажется стартовать. Некорректное значение
тоже приводит к отказу в запуске, а не к молчаливому доверию всем.

## Логи

pino, JSON, время в ISO-8601. Защита от утечки секретов двухуровневая, потому что редакции
по имени поля недостаточно: секрет может находиться внутри произвольного текста.

1. **По имени поля.** `pin`, `code`, `token`, `authorization`, `cookie`, `set-cookie`,
   `password`, `secret`, `phone` и однокоренные заменяются на `[redacted]` на любой глубине.
2. **По содержимому строки.** Каждое строковое значение, текст сообщения, текст и стек ошибки
   и вложенная причина ошибки очищаются от: учётных данных внутри URI
   (`postgresql://user:password@host`), JWT, схем `Bearer`/`Basic`, пар вида
   `password=…`, `token=…`, `api_key=…` и телефонов в российском формате.

Второй уровень обязателен: сообщение об ошибке подключения к PostgreSQL содержит строку
подключения с паролем, и именно такая ошибка попадает в лог из readiness-пробы.

Prisma настроена на `emit: 'event'` и пишет через общий логгер. Вывод Prisma по умолчанию
шёл бы напрямую в stdout мимо редакции. Стартовая ошибка в stderr тоже очищается: до создания
логгера сообщение проходит через ту же функцию.

Объекты запроса и ответа сериализуются по белому списку полей (метод, путь, код ответа,
requestId), строка запроса из пути вырезается — она может содержать телефон или код.

## Заказы доставки

Модель этапа 3.1 опирается на подтверждённые исследованием поля (`docs/MOYSKLAD_MAPPING.md`).

- **`DeliveryOrder`** — текущее состояние импортированной карточки: внешний UUID
  `customerorder` как ключ идемпотентности, номер, `updated`, внешний статус, склад
  и способ доставки, дата и её исходная строка, интервал и результат его разбора, адрес,
  получатель, комментарий, тип оплаты, деньги, признаки области и «Требует внимания».
  Физическое удаление запрещено триггером: заказ выходит из области, но не стирается.
  `externalId` защищён отдельным триггером неизменяемости — уникальность не мешает
  переписать ключ идемпотентности у существующей строки, а после такой правки импорт
  создал бы дубликат и потерял историю. Склад и способ доставки nullable: у ранее
  импортированного заказа значение может исчезнуть, и он обязан сохраниться
  с `inScope = false`, а не уронить проход синхронизации.
  Плановая дата — колонка типа `DATE` с календарной датой Москвы: тип с временем
  позволил бы часовому поясу перенести доставку на соседний день.
  Финансовые правила защищены `CHECK`-ограничениями: наличные возможны только при
  точном типе оплаты, сумма к получению равна `max(0, sum − payed)` и обнуляется при
  любом другом типе, денежная аномалия существует только вместе с наличными,
  а все денежные поля неотрицательны.
- **`DeliveryOrderRevision`** — неизменяемая история внешних версий. Хранит канонический
  снимок только подтверждённых полей, его SHA-256 и список реально изменившихся полей.
  `UPDATE` и `DELETE` запрещены триггерами. Полный ответ API не сохраняется.
- **`IntegrationCursor`** — рабочее состояние синхронизации: курсор по `updated`, признак
  завершённой первоначальной загрузки, время последней сверки. Отделён от
  `IntegrationStatus.details`, который остаётся отображаемой диагностикой.

Разделение истории и аудита намеренное: значения полей заказа лежат в защищённой ревизии,
а общий `AuditLog` фиксирует факт и список изменённых полей — иначе персональные данные
дублировались бы в двух местах с разными правилами доступа.

**Деньги** хранятся целыми копейками в `BigInt`. Единица подтверждена сверкой ответа API
с карточкой заказа. Числа с плавающей точкой не используются: от этих значений зависит
долг курьера. На границе JSON API денежные значения передаются десятичными строками —
`bigint` не сериализуется, а `number` теряет точность на больших суммах.

## Маршруты

Модель этапа 4.1 покрывает только ручные черновики: подтверждение, отмена и мягкая
блокировка редактора появятся в 4.2, отгрузка — на этапе 6.

- **`DeliveryRoute`** — маршрут одной календарной даты. Номер вида `R-2026-08-07-003`
  выдаётся атомарно счётчиком `RouteNumberCounter` одним оператором
  `INSERT … ON CONFLICT DO UPDATE … RETURNING` в той же транзакции, что и создание
  маршрута: откат создания откатывает и номер, а два одновременных создания получают
  разные номера без внешней блокировки. Персональных данных номер не содержит.
  Дата после создания неизменна — защищено триггером: правка даты у существующего
  маршрута молча нарушила бы правило «в одном маршруте только заказы одной даты».
  Физическое удаление запрещено триггером.
- **`RouteOrder`** — участие заказа в маршруте с историей. Строка не удаляется
  и не оживляется: повторное добавление ранее убранного заказа создаёт новую запись.
  Триггер запрещает подменять маршрут, заказ и автора добавления, возвращать удалённое
  участие в активное и переписывать зафиксированное удаление.
- **`RouteOrderConflict`** — неизменяемые расхождения распределённого заказа
  с маршрутом. Отдельная таблица, а не поле: заказ может одновременно сменить дату,
  выйти из области и оказаться архивированным. Пара «участие + вид» уникальна, поэтому
  повторный overlap-проход синхронизации не создаёт дубликат и не уведомляет второй раз.

Инварианты закреплены базой: частичный уникальный индекс `("orderId") WHERE "removedAt"
IS NULL` не даёт заказу попасть более чем в один активный состав (он же запрещает
повтор внутри одного маршрута), частичный уникальный индекс `("routeId","position")`
делает порядок доставки однозначным, `CHECK` требуют позиции от единицы, полноты
удаления, обязательного целевого маршрута ровно при перемещении и неотрицательных
версий. Все внешние ключи — `ON DELETE RESTRICT`.

**Внутреннее состояние заказа не хранится колонкой.** `UNASSIGNED`, `IN_DRAFT`
и `CONFIRMED` вычисляются из активного участия и состояния маршрута. Отдельное поле
было бы вторым источником истины, который база согласовать не может: сочетание
«активное участие есть, а заказ считается нераспределённым» просто не должно
существовать.

## Жизненный цикл маршрута и мягкая блокировка редактора

Этап 4 знает три состояния и ровно четыре перехода: `DRAFT → CONFIRMED`,
`CONFIRMED → DRAFT`, `DRAFT → CANCELLED`, `CONFIRMED → CANCELLED`. Список закреплён
`CHECK`-ограничением на `RouteStateTransition`: запись в неизменяемую историю нельзя
исправить постфактум, поэтому ошибочный переход не должен туда попасть вовсе.
`ACTIVE` и `COMPLETED` появятся на этапе 6 отдельной forward-only миграцией.

- **`RouteStateTransition`** — неизменяемая история: кто, когда и почему менял состояние.
  `UPDATE` и `DELETE` запрещены триггером. Причина обязательна при возврате в черновик
  и при отмене (3–500 символов) и запрещена при подтверждении: подтверждение и есть
  согласие. Причина живёт только здесь и в защищённом аудите — в realtime она не уходит.
- **Подтверждение — повторная проверка, а не формальность.** Между добавлением заказа
  и подтверждением проходят минуты, за которые синхронизация могла сменить дату, вывести
  заказ из области или пометить его пропавшим. Поэтому состав проверяется заново
  по текущим полям заказов. «Требует внимания», отсутствующий интервал и адрес
  подтверждение не блокируют — они остановят отгрузку на этапе 6.
- **Отмена** закрывает все активные участия причиной `ROUTE_CANCELLED`; строки остаются
  историей, а заказы снова становятся вычисляемо нераспределёнными.

**`RouteEditLease`** — мягкая блокировка редактора черновика. Жёсткая блокировка
не годится: она держала бы открытой транзакцию всё время, пока человек думает над
порядком доставки. Аренда живёт 90 секунд, продлевается сердцебиением раз в 30 секунд,
истекает сама и может быть перехвачена с подтверждением, причиной и версией аренды.
Держатель — пара «пользователь + семья сессий»: один человек с двух устройств считается
двумя редакторами, иначе второе устройство молча перетирало бы правки первого.
Семья сессий наружу не возвращается никогда. Время только серверное.

Аренда обязательна для всех изменений черновика, включая подтверждение и отмену
черновика; перемещение требует аренды обоих маршрутов. Создание черновика и возврат
из подтверждённого сразу выдают аренду инициатору. Подтверждённый маршрут не
редактируется вовсе, поэтому возврат в черновик арендой не защищён.

## Порядок блокировок при работе с маршрутами

Пользовательские операции:

```
DeliveryRoute (FOR UPDATE, все затронутые, ORDER BY id)
  → RouteEditLease (FOR UPDATE, по routeId в том же порядке)
  → DeliveryOrder (FOR UPDATE, ORDER BY id)
  → активные RouteOrder → RouteOrderConflict → RouteStateTransition
  → AuditLog → RealtimeEvent
```

Сортировка по UUID обязательна: два встречных перемещения между одними и теми же
маршрутами при произвольном порядке дали бы взаимную блокировку.

Синхронизация МоегоСклада использует **другой поток** и начинает с заказа:

```
advisory-lock прохода → DeliveryOrder (FOR UPDATE)
  → чтение активного RouteOrder → RouteOrderConflict → AuditLog → RealtimeEvent
```

Блокировку `DeliveryRoute` импорт не берёт намеренно — иначе появился бы обратный
порядок «Order → Route» против пользовательского «Route → Order». `markSourceMissing`
идёт по тому же пути: сначала строка заказа, затем участие. Внешних запросов внутри
транзакций нет ни в одном потоке.

Применение плана (этап 5.4) — третий поток. Он начинает с запуска планирования,
существующих маршрутов не блокирует и потому в цикл с пользовательскими
операциями не входит:

```
RoutePlanRun (FOR UPDATE)
  → DeliveryOrder (FOR UPDATE, ORDER BY id)
  → Depot (FOR UPDATE, ORDER BY id)
  → RouteNumberCounter → DeliveryRoute → RouteOrder
  → AuditLog → RealtimeEvent
```

Смена склада по умолчанию берёт выделенную advisory-блокировку `730206`
до любых строк складов: одна операция на все изменения состава и умолчания.

## Геоданные заказа

Координаты хранятся целыми микроградусами и существуют только в состоянии
`geoState = RESOLVED` — это закреплено ограничениями PostgreSQL, а не только кодом.
История `OrderGeoHistory` неизменяема триггерами. Стек карт, границы провайдеров
и правила приватности описаны в `docs/GEO_ARCHITECTURE.md`.

Установка точки блокирует только строку заказа:

```
DeliveryOrder (FOR UPDATE) → OrderGeoHistory → AuditLog → RealtimeEvent
```

Маршруты при этом не блокируются: точка принадлежит заказу, а не маршруту,
и брать здесь `DeliveryRoute` значило бы построить порядок «Order → Route»
против пользовательского. Инвалидация точки при смене адреса выполняется внутри
транзакции синхронизации, которая уже держит ту же строку заказа.

## Очередь геокодирования

`OrderGeocodeJob` — вторая очередь в системе, отдельная от `OutboxMessage`.
Причина техническая и жёсткая: обработчик outbox вызывается **внутри
транзакции**, а обращение к внешнему сервису длится сотни миллисекунд.
Транзакция, открытая всё это время, держала бы соединение с пулом и строку
заказа, и логист не смог бы поставить точку руками, пока провайдер думает.

Поэтому одно задание проходит три шага: короткая транзакция захвата и чтения
адреса → HTTP вне любой транзакции → короткая транзакция применения результата.
Между первым и третьим шагом заказ мог измениться, поэтому третий шаг блокирует
его заново и перепроверяет поколение адреса, сам адрес, область и наличие ручной
точки. Несовпадение означает устаревший результат: задание закрывается,
заказ не меняется.

Порядок блокировок при применении:

```
DeliveryOrder (FOR UPDATE) → OrderGeocodeJob → OrderGeoHistory
  → AuditLog → RealtimeEvent
```

Обращения к провайдеру защищены session advisory-lock с собственным ключом:
экземпляров приложения может быть несколько, а лимит и баланс у провайдера
общие. Ключ синхронизации не переиспользуется — это разные сервисы с разными
лимитами, и общий замок заставил бы их ждать друг друга.

## Картографические артефакты и маршрутизатор

Подложка и дорожный граф — это гигабайты, которые не хранятся ни в Git, ни
в образе приложения. Они кладутся на сервер отдельной операцией, монтируются
только на чтение и описаны манифестом с контрольными суммами. Приложение
проверяет их один раз при старте: несовпадение означает «Карта не настроена».

Артефакты раздаёт само приложение по пути `/maps`, а не отдельный сервис.
Так происхождение стиля, шрифтов, спрайтов и PMTiles совпадает с интерфейсом
само собой — без правил CORS и без второго публичного порта. Наружу всё
выводится обратным прокси по HTTPS.

Valhalla живёт внутри сети Compose и наружу не публикуется. Её адрес известен
только серверу; в браузер он не попадает никогда, а в саму Valhalla уходят
только координаты.

Смена идентичности графа выполнена расширением схемы: колонка `graphRevision`
осталась на месте и по-прежнему заполняется, рядом появилась `graphSha256`.
Причина — устройство выкатки: при неудачном запуске новой версии продолжает
работать прежняя, с той же схемой. Переименование колонки превратило бы этот
запасной путь в ловушку. Удаление старой колонки — отдельная contract-миграция
после обновления всех окружений.

**Идентичность дорожного графа определяется содержимым — SHA-256 файла
`tiles.tar`.** Оно же входит в ключ кэша матриц. Время изменения файла
и `tileset_last_modified` из `/status` — метки файловой системы: они меняются
при копировании набора и не меняются при подмене его содержимого, поэтому
идентичностью служить не могут и с ревизией не сравниваются. Метка времени
остаётся диагностикой и признаком того, что набор загружен.

Решатель VROOM живёт в ОТДЕЛЬНОЙ внутренней сети Compose. Полностью отрезать его
от сети (`--network none`) невозможно: приложение обязано отправлять ему HTTP.
Поэтому изоляция строится не отсутствием сети, а отсутствием доступа к ней
снаружи: сеть объявлена `internal`, портов не публикуется, приложение подключено
к обеим сетям, решатель — только к внутренней.

Возможность решателя проверяется поведением, а не номером версии из настройки:
и выкатка, и приложение при старте отправляют ему крошечную задачу, в которой
время обслуживания задано только через `service_per_type`. Решатель версии ниже
1.15.0 неизвестный ключ проигнорирует и вернёт правдоподобный план с нулевым
временем обслуживания — такой план выглядит выполнимым и таковым не является.

Кэш матриц — третья очередь в системе со своим способом взаимного исключения.
Здесь его роль играет уникальный индекс ключа: `INSERT … ON CONFLICT DO NOTHING`
выдаёт право на расчёт ровно одному экземпляру, остальные ждут результат.
Сетевой вызов, как и в геокодировании, выполняется строго вне транзакции.

## Время и часовой пояс

Единственный бизнес-часовой пояс — `Europe/Moscow` (`docs/OWNER_DECISIONS.md`,
`TZ-001`). Общие функции лежат в `packages/shared/src/time.ts` и одинаково
доступны серверу и браузеру.

Три разные сущности, которые нельзя путать:

| Что               | Как хранится                        | Как показывается                            |
| ----------------- | ----------------------------------- | ------------------------------------------- |
| Абсолютный момент | UTC-инстант (`DateTime`, ISO)       | `formatMoscowDateTime` с явным поясом       |
| Календарная дата  | строка `YYYY-MM-DD`, колонка `DATE` | `formatCalendarDate`, без `new Date(value)` |
| Минуты внутри дня | целое число минут                   | `formatMinutesOfDay`, пояс не участвует     |

**Обязательное правило для новых экранов и модулей.**

- Не вызывать `toLocaleString`/`toLocaleDateString`/`toLocaleTimeString` без
  явного `timeZone`. Без него показывается время компьютера пользователя,
  и один и тот же заказ выглядит по-разному у логиста и у владельца в поездке.
- Не вычислять «сегодня» через локальные геттеры `Date` и не писать собственное
  смещение `+3`. Московский день считает `moscowToday` из `@fl/shared`.
- Не превращать строку `YYYY-MM-DD` в `Date` ради показа: западнее Гринвича
  такой разбор отдаёт предыдущий день.
- Абсолютная шкала базы — **UTC**, бизнес-календарь и показ — Москва. Пояс
  PostgreSQL задан дважды: `TZ`/`PGTZ=Etc/UTC` в окружении контейнера и
  `timezone=UTC` в параметрах запуска сервера. Двойное задание не избыточно:
  переменные окружения действуют на новый кластер и на клиентов внутри
  контейнера, а уже созданный том хранит собственный `timezone`
  в `postgresql.conf`, и перекрывает его только параметр запуска.
- Пояса базы и приложения РАЗНЫЕ намеренно, и выравнивать их нельзя: это
  вернуло бы расхождение, при котором значение, записанное самой базой, ложилось
  на три часа впереди соглашения «в колонке лежит UTC». Закреплено проверками
  `apps/api/src/platform/time-model.critical.test.ts`
  и `deploy/deploy-scripts.critical.test.ts`.

Проверки часового пояса выполняются под чужими поясами (`TZ=UTC` и
`TZ=America/Los_Angeles`): ошибка границы суток видна только там, где дата
отличается от московской.
