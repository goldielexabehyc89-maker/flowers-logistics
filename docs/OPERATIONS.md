# Эксплуатация

## Проверки работоспособности

| Проба         | Что проверяет                                   | Поведение при отказе                            |
| ------------- | ----------------------------------------------- | ----------------------------------------------- |
| `GET /health` | процесс жив; внешние зависимости не проверяются | 5xx только при падении процесса                 |
| `GET /ready`  | база отвечает, ограничение 5 секунд             | `503` с телом `{"checks":{"database":"error"}}` |

`/health` намеренно не трогает базу: иначе недоступность PostgreSQL приводила бы к бесконечному
перезапуску контейнера вместо честного «не готов». Балансировщик и деплой ориентируются на `/ready`.
Проба ограничена по времени — проба без предела ожидания бесполезна.

Тексты ошибок базы наружу не отдаются: строка подключения содержит пароль.

## Логи

Формат — JSON, одна строка на запись, время в ISO-8601, часовой пояс `Europe/Moscow`.
Обязательные поля: `level`, `time`, `service`, `env`, `msg`; у запросов дополнительно
`reqId`, `req.method`, `req.path`, `res.statusCode`, `responseTime`.

Редактируются на любой глубине вложенности: `pin`, `code`, `token`, `accessToken`,
`refreshToken`, `authorization`, `cookie`, `set-cookie`, `password`, `secret`, `pepper`,
`apiKey`, `credential`, `phone`. Строка запроса из пути вырезается.

Уровень задаётся `LOG_LEVEL` (`info` по умолчанию). Уровень `debug` на production включается
только временно и осознанно: он повышает объём и риск попадания лишнего в лог.

## Резервное копирование PostgreSQL

**Важно:** `pg_dump` запускается той же мажорной версией, что и сервер. На машине разработчика
установлен клиент PostgreSQL 14, который не может дампить PostgreSQL 16, поэтому все операции
выполняются **внутри контейнера** `postgres:16`.

```bash
# Резервная копия (локальное окружение)
docker compose exec -T db pg_dump -U fl_app -d fl_dev -Fc > "backup-$(date +%Y%m%d-%H%M).dump"

# Восстановление в чистую базу
docker compose exec -T db pg_restore -U fl_app -d fl_dev --clean --if-exists < backup.dump
```

Требования к staging и production (настраиваются вместе с агентом-администратором):

- автоматические копии базы и файлов по расписанию;
- хранение вне того же сервера;
- **обязательная регулярная проверка восстановления** — резервная копия, из которой ни разу
  не восстанавливались, не считается резервной копией;
- перед каждой production-выкаткой — свежая копия и проверка свободного места.

Дампы содержат PII и в Git не попадают: `*.dump`, `*.sql.gz`, `backups/` перечислены
в `.gitignore`.

## Тестовая база

Критические тесты инвариантов **разрушающие**: они создают пользователей и записи аудита,
которые невозможно удалить (защищены триггерами). Поэтому они допускаются только к одноразовой
базе `fl_test` локально и `fl_ci` в CI.

```bash
./scripts/reset-test-db.sh                          # пересоздаёт fl_test и применяет миграции
docker compose run --rm app npm run test:critical
```

Защита реализована в коде (`apps/api/src/platform/testing/test-database.ts`) и отказывает
при попытке запуска против `fl_dev`, а также при `APP_ENV`/`APP_ENVIRONMENT_MARKER`, равном
`staging` или `production`, — независимо от имени базы. Скрипт пересоздания принимает только
имена `fl_test` и `fl_ci`.

## Миграции

Только forward-only. Применённая миграция не редактируется — исправление оформляется новой.

```bash
docker compose run --rm app npx prisma migrate status
docker compose run --rm app npx prisma migrate deploy
```

`prisma migrate reset` на общей и боевой базе запрещён: он удаляет данные.

## Время в базе и на экране

PostgreSQL работает в **UTC**, приложение — в **`Europe/Moscow`**. Это не
рассогласование, а два уровня одного решения (`docs/OWNER_DECISIONS.md`,
`TZ-001`): база хранит абсолютную шкалу, а «сегодня», интервалы и показ
человеку считает приложение.

Практическое следствие для дежурного:

```bash
docker exec <db-контейнер> psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c 'SHOW TimeZone'
```

выдаёт `UTC`, и любые отметки времени в выводе `psql` — **UTC-инстанты**.
Московское время из них делает приложение при показе. Чтобы посмотреть значение
глазами пользователя, добавьте пояс прямо в запрос:

```sql
SELECT "occurredAt" AT TIME ZONE 'UTC' AT TIME ZONE 'Europe/Moscow' FROM "AuditLog" LIMIT 1;
```

Сравнивать колонку с `now()` без приведения нельзя: `now()` — это `timestamptz`,
и без явного `AT TIME ZONE 'UTC'` сравнение однажды соврёт. Раньше сервер базы
работал в московском поясе, и такое сравнение показывало ложный сдвиг на три
часа у совершенно исправных строк.

Время в колонки пишет приложение. `DEFAULT CURRENT_TIMESTAMP` в схеме остаётся,
но продуктовые пути до него не доходят.

## Диагностика частых ситуаций

**`/ready` отвечает 503.** Проверить контейнер базы (`docker compose ps db`), затем
`docker compose exec db pg_isready -U fl_app -d fl_dev`. В логе приложения будет запись
`readiness: база данных недоступна` с технической причиной.

**Порт 55432 занят.** На машине могут работать другие проекты. Порт хоста переопределяется:
`DB_HOST_PORT=55433 docker compose up -d db`.

**`npm ci` не ставит зависимости.** Зависимости живут в томах Docker, а не в рабочей папке:
на macOS запись десятков тысяч файлов через bind-mount занимает десятки минут. Сбросить том:
`docker compose down -v` удалит **и данные базы** — для сброса только зависимостей
`docker volume rm flowers-logistics_app-node-modules`.

**Установка предупреждает про install scripts.** npm 11+ требует явного одобрения.
Разрешённые пакеты перечислены в `allowScripts` в `package.json` и проходят ревью в PR.

## Камера склада не открывается

Камера — третий способ ввода. Если она недоступна, склад продолжает работать
внешним сканером-клавиатурой и ручным вводом: это не аварийная ситуация,
а штатный запасной путь, и смену останавливать не нужно.

Что проверить по порядку:

1. **Соединение защищённое.** Браузер отдаёт камеру только по HTTPS (и на
   `localhost`). По обычному HTTP кнопка покажет честный текст и предложит
   сканер либо ручной ввод — это не поломка приложения.
2. **Разрешение выдано.** Отказ запоминается браузером: снять его нужно
   в настройках сайта на самом устройстве. Приложение повторно спросить
   не может.
3. **Камера не занята другим приложением.** Вторая вкладка или программа
   видеосвязи удерживают устройство.
4. **Устройство есть.** На стационарном компьютере без камеры остаётся
   аппаратный сканер: он работает как клавиатура и настройки не требует.

Кадры не покидают устройство: распознавание идёт в браузере, на сервер уходит
только строка кода. Поэтому по журналам сервера отличить камеру от сканера
нельзя и не нужно — операции одинаковые.

**Что не является поломкой.** Экран сканирования не закрывается между шагами
одной цепочки — так задумано. Он закрывается после завершённой цепочки или по
кнопке «Отмена». Отмена не откатывает уже подтверждённые операции: выданные
заказы остаются выданными, перенесённые — перенесёнными.

## Снимок заказов для staging

> **Это один из двух путей, которыми заказы попадают на staging.** Второй —
> собственная синхронизация staging с живым МоимСкладом, разрешённая решением
> владельца `ENV-004` строго на чтение. Там поля заказов **реальные**, а не
> псевдонимы; правила ниже относятся именно к переносу снимка между окружениями
> и своей силы не теряют. На момент написания собственная синхронизация staging
> ещё не включена: интеграция там числится `NOT_CONFIGURED`.

Staging получает **только заказы и только в одну сторону**: production → staging. Обратного
переноса нет. Полный клон базы запрещён: в нём оказались бы пользователи, PIN-хеши, сессии,
коды активации, аудит, outbox и настройки. Запрет полного клона действует независимо
от того, каким путём заказы попали на staging.

Механизм: `exportOrdersSnapshot` собирает снимок из уже импортированной копии заказов,
`assertSnapshotIsSafe` проверяет его перед импортом. К МоемуСкладу выгрузка не обращается.

**Что переносится.** Номер, дата доставки, интервал (включая ручной), суммы в копейках,
признаки наличных и переплаты, внешний статус, признаки области и внимания. Заказы без
распознанной даты включаются намеренно: именно они наполняют «Требует внимания».

**Что не переносится никогда.** Токен МоегоСклада и любые секреты, пользователи, роли, PIN,
сессии, аудит, outbox, realtime-события, курсор интеграции, внешние идентификаторы
МоегоСклада, а также адрес, получатель и текст комментария.

**Псевдонимы вместо персональных данных.** Адрес и получатель заменяются устойчивым хешем
с секретной солью: одно значение — один псевдоним, поэтому группировка по адресу на staging
работает, а восстановить исходное значение без соли нельзя. Соль хранится только
на production и в снимок не попадает — уезжает лишь её отпечаток. От комментария остаётся
только признак «был».

**Команды.** Обе разрешены только при `APP_ENV=staging` и маркере `staging`, читают один
явный абсолютный файл без масок и не выводят наружу ни содержимого снимка, ни псевдонимов,
ни координат, ни сумм — только количества:

```
npm run snapshot:import -- --file /абсолютный/путь/snapshot.json
npm run snapshot:retire -- --file /абсолютный/путь/snapshot.json
```

Эти имена запускают собранные файлы и потому работают внутри production-образа
на сервере. В контейнере разработки, где собранного файла может не быть,
используются варианты с суффиксом `:dev` — тот же контракт у `bootstrap:admin`
и `moysklad:sync-once`.

Импорт различает пять исходов: `создано`, `обновлено`, `без изменений`, `возвращено
в область`, `без синтетической точки`. Идентичный повтор не пишет ВООБЩЕ ничего — ни версии,
ни времени обновления, ни аудита, ни события: повторный прогон обязан быть неотличим
от невыполненного, иначе он сам становится изменением данных.

**Очистка набора.** Физического удаления нет: `DeliveryOrder` защищён триггером базы,
и это правильно — заказ может перестать быть нашим, но не может исчезнуть из истории.
`snapshot:retire` выводит заказы набора из области существующим доменным путём
(`sourceMissing = true`, `inScope = false`, причина `SOURCE_MISSING`): они пропадают
из планирования, нераспределённых и карты, оставаясь в истории. Команда работает только
по ключам переданного снимка, сначала выполняет сухую проверку, ничего не удаляет,
а повторный вызов — безопасное бездействие. Повторный импорт того же файла возвращает
те же записи и те же синтетические точки.

Если хотя бы один заказ набора состоит в **активном маршруте**, команда отказывается
целиком и называет номера маршрутов. Маршруты отменяет человек через интерфейс: отмена
требует причины и остаётся его решением, а не следствием запуска скрипта.

**Ограничения на сегодня.** Реального production не существует, поэтому механизм проверен
только на тестовых базах, а выгрузка и расписание не реализованы. Ограничение выборки —
по нижней границе даты доставки и явному лимиту. Импорт fail closed: неизвестный формат,
следы секретов, настоящий адрес вместо псевдонима или неполный ручной интервал
останавливают импорт целиком, до единой записи.

**Ручной интервал** переносится только полным комплектом из трёх полей, включая время
установки: база не принимает половинчатое значение, а «интервал есть, но неизвестно
с каких пор» — не факт, а его видимость. Исходный текст интервала на staging не
переносится вовсе: он написан человеком про конкретный заказ. Вместо него импорт выводит
текст из уже разобранного вида — он честно описывает то, что лежит в минутах.

**Адреса для проверки маршрутов — решение владельца (07.08.2026).** Используется отдельный
набор синтетических, но валидных адресов Москвы: точки распределены и внутри МКАД, и за ним,
чтобы проверялись и городские маршруты, и выезды. Псевдоним адреса стабильно сопоставляется
одной и той же точке набора, поэтому один и тот же заказ на staging всегда попадает в то же
место, а группировка по адресу сохраняется.

Настоящие адреса в staging не переносятся ни в каком виде. Вариант «улица без дома
и квартиры» отклонён: это по-прежнему реальные данные клиента, а для геокодирования
такой адрес всё равно непригоден.

Сам набор точек появится вместе с подключением карт (этап 5); в этой ветке реализован только
перенос заказов с псевдонимами.

## Карта

Адрес стиля карты задаётся переменной `MAP_STYLE_URL`, подпись правообладателя —
`MAP_ATTRIBUTION`. Обе необязательны.

Если `MAP_STYLE_URL` не задан, `GET /api/map/config` отвечает `configured: false`,
интерфейс показывает «Карта не настроена», а маршрутизация продолжает работать
списком. Это осознанное поведение: подставлять публичный сервер OSM или
демонстрационные тайлы MapLibre запрещено — их условия не допускают продуктовую
нагрузку.

Ключи картографических сервисов в браузер не передаются: конфигурация отдаёт
только адрес стиля и подпись.

**Картографические архивы в Git не хранятся.** Файлы `.pmtiles`, `.mbtiles`
и `.osm.pbf` раздаются отдельно и никогда не кэшируются service worker: это единые
файлы на сотни мегабайт, из которых карта читает куски диапазонными запросами.
Собственная подложка появится на этапе 5.3.

## Геокодирование адресов

Переменные окружения: `PHOTON_URL`, `DADATA_API_KEY`,
`DADATA_GEOCODING_ENABLED`.

Приложение **не запустится**, если ключ или включённый флаг обнаружены там,
где они недопустимы (маркеры окружения не совпали, `local`, CI), либо если
включённые подсказки не имеют ключа. Это осознанный fail closed: ключ
расходует платный баланс организации, а каждый запрос содержит адрес клиента.

**Ключ ровно один — `DADATA_API_KEY`.** Секретный ключ (`X-Secret`) требовался
платному Clean API, которого в проекте нет; переменной `DADATA_SECRET_KEY`
больше не существует. Если она осталась в приватной конфигурации сервера,
её значение не читается и никуда не отправляется — строку следует удалить.

Ключи DaData автоматического геокодирования **не включают**. Начиная
с `GEO-005` их единственное назначение — подсказки адреса в ручной правке;
платный `Clean API` не вызывается нигде.

**Автоматический геокодер — собственный Photon.** Worker создаётся ровно при
одном условии: задан `PHOTON_URL`. Окружение здесь не проверяется намеренно —
свой сервис не тратит чужих денег и не отдаёт адреса наружу. Пустое значение
означает «геокодер не настроен»: заказы остаются в «Требует внимания», и точку
ставит человек. Публичные `photon.komoot.io` и `nominatim.openstreetmap.org`
отвергаются до обращения к сети.

**Порядок включения.** Задать `PHOTON_URL` на уже работающий собственный Photon
и перезапустить приложение. При старте очередь автоматически наполняется уже
импортированными заказами в состоянии `UNRESOLVED` — небольшими пачками,
только подходящими заказами и без повторной постановки. Для ограниченного
прохода с явным потолком обращений есть отдельная команда:

```
npm run geocode:backfill -- --limit 200   # ограниченный проход
npm run geocode:backfill -- --report-only # только сводка, без запросов
```

Вывод содержит **только числа**: адресов всего, точно найдено Photon,
неоднозначно, не найдено, отказ геокодера, исправлено через подсказку DaData,
точка поставлена руками, ещё в очереди, адресов в кэше, запросов сэкономил кэш
и фактическое число запросов за проход.

**Наблюдение.** Состояние живёт в `IntegrationStatus` под provider `photon`
отдельно от карты. Провайдер назван по тому, кто действительно геокодирует:
прежнее имя `dadata` показывало бы дежурному состояние чужого сервиса вместо
своего. Публичный `/api/status` отдаёт только высокоуровневое состояние;
`/api/status/integrations` (только ADMIN) добавляет число заданий в очереди
и очищенные технические детали — коды отказа и причины. Ключей, адресов,
координат, заголовков и тел ответов провайдера там нет.

**Если геокодирование не работает.** Ручная установка точки доступна всегда
и не ждёт внешнего сервиса. `ERROR` у provider `photon` означает отказ, который
сам не пройдёт (`NOT_CONFIGURED`, `PUBLIC_ENDPOINT_FORBIDDEN`) и требует
человека; `DEGRADED` — временный отказ, который очередь повторит сама.

**Остановка обращений.** При неверной настройке обращения прекращаются целиком:
отметка живёт в `GeocodingProviderState.haltedReason`. Задания при этом
не теряются и попыток не тратят — они ждут в очереди. Отметка снимается **только
при запуске приложения**, поэтому порядок восстановления такой: исправить
`PHOTON_URL` и перезапустить сервис. Если адрес по-прежнему неверен, обращения
остановятся снова после первого же ответа.

**Недоступность Photon паузу делает общей.** Отказ сервиса и обрыв связи
относятся ко всему геокодеру, а не к одному адресу: проход прекращается,
остальные задания возвращаются в очередь без расходования попыток, а пауза
растёт вместе с числом попыток — от 30 секунд до 15 минут.

## Индекс геокодера

Индекс Photon — такой же неизменяемый артефакт, как подложка и дорожный граф:
он лежит **вне Git и вне образа**, монтируется только на чтение и на сервере
**не собирается**. Сборка требует Nominatim, 6 ГБ памяти и получаса; на рабочем
сервере ей делать нечего. Готовый архив приезжает извне.

Раскладка на сервере:

```
<каталог окружения>/photon/
  lib/photon.jar          исполняемый файл, сумма сверяется при каждой выкатке
  msk-mo-<дата>/          версионный каталог: photon_data/ и manifest.md
  current -> msk-mo-<дата>   символьная ссылка на действующую версию
```

### Установка новой версии индекса

```
# 1. Доставить архив и сверить сумму НА СЕРВЕРЕ.
sha256sum -c <<< "<ожидаемая сумма>  photon-msk-mo-<дата>.tar.zst"

# 2. Распаковать в НОВЫЙ каталог. Никогда не поверх работающего:
#    документация Photon прямо предупреждает, что это повреждает базу.
mkdir -p photon/msk-mo-<дата> && cd photon/msk-mo-<дата>
zstd -dc ../../photon-msk-mo-<дата>.tar.zst | tar xf -

# 3. Переключение — атомарная подмена ссылки. `ln -sfn` для этого не годится:
#    он снимает старую ссылку и создаёт новую, и между этими действиями
#    каталога не существует вовсе. `mv -T` выполняет rename(2) — одну операцию.
ln -sfn msk-mo-<дата> photon/current.new
mv -T photon/current.new photon/current

# 4. Пересоздать контейнер: bind-монтирование разрешается при старте.
docker compose up -d --force-recreate photon
```

Прежние версии **не удаляются**: откат — это подмена ссылки обратно, и он
должен занимать секунду, а не выкатку.

### Что проверяет выкатка

Перед запуском приложения и **до миграций**:

- сумма `photon/lib/photon.jar` пересчитывается на сервере;
- `photon/current` указывает на существующий каталог с непустым `photon_data`;
- рядом лежит `manifest.md` — иначе происхождение набора неизвестно;
- геокодер отвечает `Ok` на `/status` **и** находит публичный ориентир.

Последнее важно: пустой индекс на `/status` отвечает так же. Проверка поиском
отличает «геокодер работает» от «геокодер запустился».

### Границы

- Порт `2322` наружу **не публикуется** ни в одном окружении.
- Геокодер живёт во внутренней сети без выхода в интернет: даже ошибочная
  настройка не приведёт к обращению к публичному `photon.komoot.io`.
- Память ограничена 1.5 ГБ, куча JVM — `-Xmx768m`. Без явного `-Xmx` JVM берёт
  четверть памяти машины.
- Обращается к геокодеру только приложение, по имени `http://photon:2322`.

## Картографические артефакты

Наборы лежат вне Git и вне образа: `MAP_ARTIFACTS_PATH` для подложки,
`VALHALLA_GRAPH_DIR` для дорожного графа. Оба каталога монтируются **только
на чтение** и **никогда не перезаписываются на месте** — новая сборка кладётся
в каталог с новым именем, а конфигурация переключается на неё. Приложение
читает файлы прямо сейчас, и подмена под ним дала бы обрывок вместо тайла.

Staging и production могут указывать на один и тот же неизменяемый набор одной
ревизии: он одинаков. Контейнеры, тома, файлы окружения и кэши при этом
остаются раздельными.

**Сборка** выполняется отдельной операцией и в CI не запускается:

```sh
./tools/geo/build-basemap.sh --input <файл.osm.pbf> --region "Москва и область" \
  --source-date <ГГГГ-ММ-ДД> --assets <каталог> --output <каталог набора>
./tools/geo/build-valhalla-graph.sh --input <файл.osm.pbf> --output <каталог графа>
./tools/geo/verify-manifest.sh <каталог набора>
```

Версии инструментов закреплены тегом и digest в `tools/geo/versions.env`.

**Идентичность дорожного графа — это SHA-256 файла `tiles.tar`.**

Единственный признак того, какой граф установлен, — контрольная сумма его
содержимого. Она записана в манифесте набора и задаётся в конфигурации
как `VALHALLA_GRAPH_SHA256`: ровно 64 шестнадцатеричных символа.

`tileset_last_modified` из `/status` и время изменения файла на диске
идентичностью **не являются** и с ревизией не сравниваются. Это метки
файловой системы: они меняются при копировании набора, восстановлении
из резервной копии и пересоздании контейнера, оставляя содержимое тем же,
и не меняются, если подменить содержимое, сохранив время. Ни в ту, ни в другую
сторону они ничего не доказывают. Такое сравнение однажды остановило исправную
выкатку после обычного копирования набора — и не остановило бы подменённый
файл. `tileset_last_modified` сохраняется как диагностика и как признак того,
что сервис прочитал набор.

По той же причине `GRAPH_REVISION` в наборах, собранных раньше, доказательством
идентичности не считается: проверка смотрит на `extract.sha256` в манифесте.

**Проверка артефактов переживает обрыв связи.** Подсчёт SHA-256 гигабайтного
набора длится минуты. Раньше он жил ровно столько, сколько держалось
SSH-соединение: обрыв канала убивал проверку, и выкатка сообщала, что артефакты
не совпали с манифестом, не установив о них ничего. Именно это и произошло
на нестабильном канале при исправных файлах.

Теперь сервер получает задание в отдельном каталоге с уникальным именем
и выполняет его сам, независимо от соединения. Клиент только запускает проверку
и опрашивает результат короткими соединениями: обрыв опроса стоит одной попытки
и ничего не перезапускает. Код возврата пишется во временный файл и атомарно
переименовывается — читатель никогда не увидит половину строки. Результат
связан с идентификатором запуска и суммой проверяющего скрипта, поэтому чужой
или устаревший результат не может быть принят за свой. Каталог задания
удаляется только после получения результата.

**Отказы различаются, и формулировки не лгут.** «Не совпадает с проверенным
содержимым» говорится ровно в одном случае: проверка дошла до конца и
установила несовпадение (код возврата 10). Внутренняя ошибка проверки (20),
исчерпанное время ожидания, потерянное задание, чужой или недописанный
результат — это «проверка не состоялась», и артефакты при этом несовпавшими
не признаются. Новая проверка автоматически не запускается: это решение
владельца.

**Выкатка fail closed.** Перед запуском проверяются манифест и контрольные
суммы подложки, а для графа — SHA-256 лежащего на сервере `tiles.tar`,
пересчитанный заново. Он обязан совпасть и с манифестом, и с конфигурацией:
манифест только объявляет, доказывает пересчёт. Любое несовпадение — отказ.
Проверки выполняются внутри закреплённого образа приложения: Node на сервере
не требуется. При `DRY_RUN=1` они пропускаются — сухой прогон обязан
обходиться без сети и без секретов.

**Порядок запуска строгий:** проверка содержимого → `valhalla` → её `/status`
→ пробная матрица на синтетических точках → **миграции** → `app` → `/ready`.

Миграции стоят предпоследними намеренно. Выкатка при отказе сохраняет прежнюю
версию — тот же контейнер, ту же схему. Применить миграции раньше проверок
значило бы менять схему под работающим старым приложением ради версии, которая
может и не запуститься. Поэтому схема меняется только после того, как всё,
что могло отказать раньше, уже прошло.

По той же причине миграции обязаны быть **расширяющими**: добавление колонок
и ограничений, без переименований и удалений. Даже успешно применённая
миграция должна оставлять схему пригодной прежней версии — на случай, если
новое приложение не поднимется. Удаление устаревшей колонки выполняется
отдельной contract-миграцией, когда все окружения гарантированно обновлены.

Маршрутизатор не поднимается на непроверенном наборе: иначе он отрапортует
о готовности по тому, что нашёл. Загруженный набор, в свою очередь, ещё
не означает работающий расчёт — тайлы могут быть прочитаны, а нужного профиля
в них не оказаться, — поэтому до запуска приложения считается маленькая матрица
обоими профилями (`auto` и `pedestrian`).

Одновременный запуск `valhalla` и `app` выглядит быстрее, но приложение
опрашивает маршрутизатор сразу при старте и успевает записать `DEGRADED`, пока
граф загружается; это состояние осталось бы в базе и после успешной проверки,
и логист видел бы «расчёт недоступен» при исправном сервисе.

Вместе неизменяемый версионный каталог, монтирование только на чтение, сверка
манифеста по пересчитанному содержимому и успешный старт маршрутизатора
и образуют доказательство того, что загружен именно тот набор.

Отказ проверки маршрутизатора останавливает выкатку **до** запуска нового
приложения: прежняя версия продолжает работать. В `/ready` маршрутизатор
намеренно не входит — его отказ не должен снимать приложение с балансировки, —
но и объявлять выкатку успешной при неработающем расчёте нельзя.

**Пути внутри набора.** Имена каталогов шрифтов содержат пробелы — настоящее
имя семейства в ресурсах protomaps выглядит как `Noto Sans Regular`, и 256
файлов глифов лежат именно там. Пробелы допустимы; браузер присылает адрес
закодированным (`Noto%20Sans%20Regular`), и это тот же файл.

Запрещено другое: абсолютные пути, пустые сегменты и `//`, сегменты `.` и `..`,
обратный слэш, управляющие символы, percent-encoding в самом имени, пробел
в начале или конце сегмента, а также выход за каталог набора — в том числе
через символическую ссылку. Одного регулярного выражения для этого мало:
`^[^/]+(/[^/]+)*$` пропускает `..`, из которых обход и собирается, поэтому путь
разбирается посегментно, а фактическое расположение файла сверяется с `realpath`
корня.

Правила у приложения и у проверки при выкатке ОДИНАКОВЫ и закреплены общим
корпусом проверок. Расхождение уже случалось: выкатка сверяла только размеры
и суммы, приложение — ещё и форму пути, и набор, признанный проверенным,
на старте объявлялся негодным.

**Подписи на карте.** Стиль рисует названия населённых пунктов, названия улиц
вдоль дорог и номера домов. Номера появляются с четырнадцатого зума — там же,
где они есть в наборе; выше MapLibre растягивает последний векторный уровень.
Названия берутся русские (`name:ru`) с откатом на общее имя. Всё рисуется
единственным семейством набора — `Noto Sans Regular`.

**Правка стиля не требует пересборки набора.** Стиль весит около килобайта
рядом с гигабайтом тайлов, и менять оформление полной пересборкой значило бы
платить сутками сборки за подпись:

```sh
./tools/geo/restyle-basemap.mjs --set <каталог набора>
./deploy/scripts/verify-geo.mjs basemap <каталог набора>
```

Инструмент пересобирает только стиль и его запись в манифесте, сверяя
контрольную сумму архива до и после: тайлы он не трогает. Новый стиль получает
НОВОЕ имя (`style-<ревизия>-r2.json`, затем `-r3`) — имена артефактов
не переиспользуются, потому что отдаются с бессрочным кэшированием, и подмена
содержимого под тем же именем оставила бы у части браузеров старый стиль на год.

На сервер передаются только два маленьких файла — новый `style-*.json`
и `manifest.json`. Приложение читает манифест при старте, поэтому изменения
вступают в силу после перезапуска приложения; тайлы, спрайты и шрифты остаются
на месте.

**Если подложка не сошлась.** Интерфейс честно показывает «Карта не настроена»
с причиной, список заказов и маршруты продолжают работать, к публичным серверам
приложение не идёт ни при каких условиях.

## Нагрузочный пилот логистики

Отвечает на один вопрос: выдерживает ли собранный стек «матрица Valhalla →
решатель VROOM» рабочий день склада. Пилот не создаёт и не меняет заказы,
маршруты, планы, настройки, аудит и realtime — он вызывает те же функции,
что и боевой расчёт, и печатает измерения.

**Две технические области записи, и только они.** Штатный путь расчёта
намеренно проходит через продуктовый кэш матриц, поэтому операторский прогон
закономерно пишет:

- `RouteMatrixCache` — аренда и результат матрицы. Ради холодного и тёплого
  пути пилот и существует: обойти кэш значило бы измерить не тот продукт;
- `IntegrationStatus` — технический статус Valhalla, который обновляет общая
  проверка графа перед первым расчётом.

Других записей быть не должно, и это не обещание в тексте. Успешный прогон
проверяется атрибутируемым поиском: по явному перечню продуктовых мест — заказы,
маршруты, ячейки, аудит, события, планы, настройки, пользователи и склады —
ищется синтетический след пилота (`pilot-order-*`, `pilot-slot-*`,
`pilot-depot`). Его появление где-либо ломает проверку. Отдельно
подтверждается, что обе разрешённые технические области действительно
заполнены этим прогоном (`pilot-isolation.critical.test.ts`).

Сравнения счётчиков всех таблиц здесь нет намеренно: база критических тестов
общая и наборы идут параллельно, поэтому чужая запись выглядела бы как наша,
а полный перебор схемы сам мешал бы соседним проверкам.

```bash
npm run logistics:pilot -- --generate 10,30,59 --profile CAR --repeats 2
npm run logistics:pilot -- --snapshot /абсолютный/путь/snapshot.json
```

Каноническое имя запускает собранный файл и работает внутри production-образа;
в контейнере разработки используется `logistics:pilot:dev`. Команде нужны
`VALHALLA_URL`, `VROOM_URL` и `VALHALLA_GRAPH_SHA256` — без них она отказывает
кодом 2 до создания базы и клиентов.

Машиночитаемый итог формата `flowers-logistics/logistics-pilot@1` уходит
в stdout, человеческая сводка — в stderr. Наружу выходят только размеры задачи,
профиль, времена этапов, попадание в кэш, число маршрутов и неразмещённых
заказов, агрегаты расстояния и времени и безопасные коды отказов. Адресов,
координат, псевдонимов и тел ответов внешних сервисов в выводе нет.

### Ворота

Каждое утверждение можно нарушить, и нарушение — явный отказ с кодом,
а не примечание:

| Ворота                                                  | Код отказа                                      |
| ------------------------------------------------------- | ----------------------------------------------- |
| матрица точного размера                                 | `MATRIX_SHAPE`                                  |
| одна ревизия графа на весь расчёт                       | `MATRIX_GRAPH_MISMATCH`                         |
| больше 60 уникальных точек — отказ ДО решателя          | `TOO_MANY_POINTS`                               |
| недостижимая пара — fail closed                         | `MATRIX_UNREACHABLE_PAIR`                       |
| решателю ушла наша матрица **и он по ней посчитал**     | `SOLVER_MATRIX_NOT_USED`                        |
| время обслуживания по типу машины передано **и учтено** | `SOLVER_SERVICE_PER_TYPE_MISSING`               |
| матрицу не удалось получить                             | `MATRIX_UNAVAILABLE`                            |
| решатель не ответил                                     | `SOLVER_UNAVAILABLE`                            |
| повтор того же входа даёт тот же план                   | `NONDETERMINISTIC_REPEAT`                       |
| жёсткие окна и точное время соблюдены                   | `WINDOW_VIOLATED`, `SOLVER_TIME_WINDOW`         |
| ни одного потерянного или удвоенного заказа             | `ORDERS_LOST_OR_DUPLICATED`, `SOLVER_PARTITION` |

Предел 60 точек — не настройка вкуса: матрица растёт квадратично, и 60 точек
это уже 3600 пар. Он совпадает с пределом боевого расчёта (`MATRIX_MAX_POINTS`).

**Ответ решателя проверяется по результату, а не по отправленному запросу.**
Наличие полей в исходящем JSON доказывает только то, что мы их отправили;
решатель мог их проигнорировать и вернуть правдоподобный ответ. Поэтому после
каждого решения расстояние маршрута пересчитывается по фактическому порядку
остановок из переданной матрицы, а время обслуживания сверяется с числом
размещённых работ и значением для типа машины. Отсутствие нужного агрегата —
отказ, а не пропущенная проверка. Отказ базы, маршрутизатора или решателя
называется своим кодом и не маскируется под испорченную матрицу.

**Снимок читается тем же безопасным слоем, что и штатные команды staging:**
один абсолютный файл, только формат `orders-snapshot@2`, отказ при настоящем
адресе, получателе или следе соли — до матрицы, решателя и базы. Из снимка
берётся только форма дня: интервалы. Координат в нём нет по построению,
поэтому точки берутся из дорожного набора.

### Первый настоящий прогон отказал, и почему

Первая операционная приёмка на staging не прошла ни одного сценария. Отказали
три разные вещи, и каждая была настоящей:

1. **60 точек, оба профиля — `400 Exceeded max locations: 2500`.** Приложение
   разрешало день из 60 точек, конфигурация графа допускала 2500 пар. Предел
   теперь один на весь продукт, см. «Предел точек» в `GEO_ARCHITECTURE.md`.
2. **Пеший профиль, 11 и 31 точка — `500 GetTags: offset exceeds size of text
list`.** Внутренний отказ Valhalla на конкретном наборе тайлов. Установлено
   сравнением: та же ошибка воспроизводится и из `tiles.tar`, и из каталога
   `tiles` того же набора, но НЕ воспроизводится на чистой пересборке из того
   же исходного PBF тем же закреплённым образом `3.8.3@sha256:70b4…`. Версию
   менять не потребовалось; дефект был в самом наборе тайлов, а сборка при этом
   отчиталась без единой ошибки.
3. **Автомобильный профиль, 11 и 31 точка — 20 и 60 недостижимых пар.** Точки
   пилота брались равномерно случайно из прямоугольника вокруг Москвы и
   попадали в парки, в воду и в отрезанные куски сети. Ворота закрывались
   правильно, но измеряли генератор.

### Дорожный набор вместо случайного прямоугольника

Пилот берёт координаты из `apps/api/src/modules/planning/road-fixture.ts` — 60
синтетических точек, каждая примагничена к дорожной сети обоими профилями,
а весь набор проверен полной матрицей 60×60 без единого пустого элемента.
Префиксы набора дают размеры 11, 31 и 60, поэтому «10, 30 и 59 заказов» —
это начало одного и того же дня, а не три разных.

Зерно по-прежнему задаёт форму дня, но координатами больше не управляет: разные
зёрна дают одни и те же точки. Это осознанная потеря — набор, который меняется
от прогона к прогону, сравнивать не с чем.

Координаты не получены из заказов, адресов, базы staging или МоегоСклада:
они вычислены из решётки вокруг общеизвестной городской точки и уточнены
ответом маршрутизатора о том, где проходит дорога. Пересобрать набор можно
командой `tools/geo/build-road-fixture.mjs`; она же обновляет вторую форму
внутри самодостаточного `deploy/scripts/verify-geo.mjs`, а направленная
проверка сверяет обе формы по координатам.

### Что теперь проверяется до миграций

Проверка выкатки больше не спрашивает «отвечает ли сервис». Она считает
**предельную** матрицу 60×60 обоими профилями на утверждённом наборе и
отдельно — минимальный набор, воспроизводивший внутренний отказ пешего профиля
(`tools/geo/foot-regression.json`, шесть точек: ни одна пара из них отказ
не давала, он проявлялся только на широком поиске). Пустой элемент, 4xx и 5xx
останавливают выкатку до миграций и до запуска нового приложения. Там же
сверяются SHA-256 и размер `valhalla.json` и эффективный бюджет обоих
профилей.

### Базовая эвристика

Рядом с планом решателя пилот считает простой воспроизводимый baseline —
«ближайшая доступная точка от склада». Это не доказательство оптимальности,
а сигнал: если решатель хуже очевидной жадной эвристики, дело не в городе.

### Внешние источники

Пилот не обращается ни к одному внешнему картографическому хосту: только
собственные Valhalla и VROOM во внутренней сети. Решение о платных источниках
(Яндекс, 2ГИС) принимается по измеренным числам, а не по ощущениям: пока
собственный стек проходит ворота, платный источник не блокирует MVP.

## Расчёт времени в пути

`VALHALLA_URL` и `MAP_ARTIFACTS_PATH` задаёт сам Compose-файл окружения:
это внутренние пути, а не настройки сервера. Наружу маршрутизатор не публикуется.

`VALHALLA_GRAPH_SHA256` обязателен и входит в ключ кэша матриц: расчёт
по другому графу — другой ответ. В ключе участвует именно содержимое: набор,
скопированный на другой сервер, остаётся тем же графом и переиспользует кэш,
а подменённый файл с прежним временем — не переиспользует.

**Расчёт физически запрещён**, пока маршрутизатор не готов: значение неверного
формата, отсутствие `tileset_last_modified` в ответе сервиса и явное
`has_tiles: false` переводят интеграцию `valhalla` в `ERROR`, и матрица
не считается вовсе. Интерфейс обещает автоматический расчёт только после
успешного подтверждения.

**Внешний `MAP_STYLE_URL` действует только в local.** На staging и production
неисправная собственная подложка означает «Карта не настроена», а не переход
на чужой сервер: подмена увела бы адреса доставок постороннему.

Пределы: `MATRIX_MAX_POINTS` (по умолчанию 60) и `MATRIX_CACHE_TTL_SECONDS`
(по умолчанию сутки). Просроченные матрицы убирает фоновая очистка.

**Живых данных о пробках нет.** Время считается по постоянным скоростям
дорожного графа; результат помечен `trafficMode: STATIC`, а интерфейс
показывает «без данных о текущих пробках». Недоступность маршрутизатора
не влияет на `/ready` и не мешает ручным маршрутам.
